# Nitpick 审查报告：Lumen AI City

> 审查日期：2026-10-07 | 快照：`HEAD 619acf5`（`main` ahead 19） | 项目类型：Monorepo / Service | 技术栈：Python 3.12 / Go 1.23 / Rust 1.82 / TypeScript 5.5 | 规模：382 个源码文件，121 个测试文件

## 总评

**5.6/10**

项目已经有清晰的领域拆分、真实闭环和 121 个测试文件，业务推进速度快，`economy-service` 当前 48/48 测试通过。但当前瓶颈已经不是“再加功能”，而是安全边界、质量门禁和数据库级测试：`ruff check` 有 314 项违规，`agent-os` 有 4 个失败测试，关键经济接口存在默认令牌与未鉴权访问风险，文档还停留在 W1/W3 里程碑。优先把安全、CI 和真实 DB 集成测试补齐，比继续叠 W5/W6 功能更有复利。

## 系统性问题

### 1. 安全契约没有随服务数量一起扩张

- **根因**：服务快速新增后，身份校验仍停留在网关局部；内部服务直接对外暴露，且沿用开发默认值。`economy-service` 直接暴露在 `ai-city/docker-compose.yml:293-300`，`ADMIN_TOKEN` 默认为 `dev-admin-token`；`README.md:126` 仍记录 W1.4，而 `docs/15-实现状态对照.md:6` 停在 W3.2，说明状态和威胁模型没有同步。
- **影响维度**：架构、安全、测试、DX。
- **级联修复**：定义统一 `AuthContext` 和服务间调用策略，把所有经济/管理端点纳入鉴权；将默认密钥改为“生产必填”，再在 compose 中只保留本地覆盖值。

### 2. 质量门禁已经落后于主分支

- **根因**：CI 定义了 lint/test/build/security，但本地 HEAD 已经出现 `ruff` 314 项违规和 agent-os 4 项失败。`ai-city/.github/workflows/ci.yml:37` 会运行 `ruff check`，`ai-city/.github/workflows/ci.yml:81` 会运行全量 pytest。
- **影响维度**：代码质量、测试、DX。
- **级联修复**：先把 `ruff` 规则收敛到当前可执行基线，再修复 4 个失败测试；引入 PR 必须通过 lint + pytest + typecheck + build 的硬门禁。

### 3. 测试金字塔底部被 mock 抽空

- **根因**：经济服务测试主要通过 `MagicMock` / `AsyncMock` 模拟 asyncpg，`ai-city/apps/economy-service/tests/conftest.py:29-36` 明确写着“mocked asyncpg pool”。真实 SQL、约束、事务隔离、迁移漂移没有稳定被验证。
- **影响维度**：架构、代码质量、测试、安全。
- **级联修复**：为核心金额路径建立真实 Postgres integration test，按 schema 自动迁移，先测 wallet/product/transaction/central_bank_ledger 的完整事务和并发。

## 各维度发现

### 1. 架构与设计（6.5/10）

- **P1 — 服务部署/CI 覆盖不一致**：`ai-city/.github/workflows/ci.yml:112-124` 只构建 `api-gateway`、`world-engine`、`agent-os`、`memory-service`、`saga-orchestrator`、`admin-portal`，缺少 `economy-service`、`ws-gateway`、`bt-editor-api` 等；而 `economy-service` 已进入 `ai-city/docker-compose.yml:288-323`。修复：把所有可部署服务纳入构建矩阵，并按服务配置 build/test 依赖。
- **P1 — 中央银行计算与更新不原子**：`compute_emit()` 在一个连接里读取 active_count 与 total_gold，`ai-city/apps/economy-service/src/economy_service/services/central_bank.py:39-56`；随后 `emit()` 在新事务里更新 wallet，`central_bank.py:68-80`。两次读之间 active wallet 数或余额可能变化，`total_distributed` 可能虚报。修复：将 count、sum、wallet lock/update 放入同一事务，或用行级锁定和实际更新行数计算。
- **P2 — 关键服务仍是显式 stub**：`memory-service` 的 pipeline 中有多个 `TODO + pass`，见 `ai-city/apps/memory-service/src/memory_service/pipeline.py:35-56`；`notification-engine` 也停留在 TODO，见 `ai-city/apps/notification-engine/src/notification_engine/dispatcher.py:32-43`。README 把 memory-service 标成完整，见 `README.md:120`。修复：在 README/roadmap 中明确 stub 状态，或将服务从 compose 默认启动集中移除。
- **P2 — post-hook 任务生命周期松散**：`ai-city/apps/agent-os/src/agent_os/dispatcher.py:116-145` 返回未 await 的 `asyncio.create_task(...)`；异常只打 warning。可接受为 best-effort，但缺少任务追踪、背压和结构化失败记录。修复：维护 per-session task set，为任务附加 trace_id，并加指标。

### 2. 代码质量（5.5/10）

- **P1 — Python 静态检查大面积失败**：当前 `uv run ruff check apps packages --statistics` 返回 314 项，其中 67 项 RUF002、57 项 I001、30 项 F401，161 项可自动修复。CI 在 `ai-city/.github/workflows/ci.yml:37` 会失败。修复：先分目录自动修复 import/格式类问题，再人工处理 F821/F841 等语义项。
- **P2 — post-hook 幂等键设计脆弱**：`ai-city/apps/agent-os/src/agent_os/bt/actions.py:72-84` 使用 `bt_tick_{state.tick_count}` 作为 `idempotency_key` 和 `trace_id`。同一 tick 的重复触发会被 Redis 幂等层拦截，造成用户以为没有购买成功但上游已显示成功。修复：使用 UUID/trace_id 作为幂等键，并将业务结果写回 BTState。
- **P2 — 前端大组件继续膨胀**：`WorldMap.tsx` 450 行，`NPCDialog.tsx` 302 行；后者在 `ai-city/web/src/components/NPCDialog.tsx:155-180` 集中处理流式事件、定时器和 UI 状态。修复：把事件 reducer、session buffer、emotion chip 拆成独立 hooks/components，并补 interaction 测试。
- **P3 — 重复 OpenAPI 待办**：`docs/15-实现状态对照.md:55-56` 连续两行都是“补 OpenAPI 导出”。修复：删除重复项并生成脚本化导出。

### 3. 安全（4.5/10）

- **P0 — 管理端令牌有公开默认值且服务直接暴露**：`ai-city/apps/economy-service/src/economy_service/api/v1/admin.py:12` 默认 `ADMIN_TOKEN = "dev-admin-token"`；compose 也注入同一默认值，`ai-city/docker-compose.yml:296-300`。管理员 emit/sink 端点可被直接访问。修复：生产模板改为必填变量，启动时缺省即 fail-fast；本地 dev 值只能通过 `.env.local` 注入。
- **P0/P1 — 经济流水可未鉴权读取**：`ai-city/apps/economy-service/src/economy_service/api/v1/transactions.py:7-21` 没有任何 `Authorization` 校验，`user_id` 完全来自路径，可枚举任意玩家交易历史。修复：网关转发校验 JWT，服务端强制 `token.sub == user_id` 或 admin scope。
- **P1 — 默认 JWT/管理员密码仍进 compose/admin 代码**：`ai-city/docker-compose.yml:109` 和 `:201` 使用 `JWT_SECRET: dev-secret-change-me`；admin 登录默认密码在 `ai-city/apps/admin-portal/src/app/api/auth/login/route.ts:35-42`。修复：生产模式下禁止默认值；本地开发单独放 `.env.local`，并加启动期 lint/脚本检查。
- **P1 — 世界移动存在 IDOR**：`ai-city/apps/api-gateway/internal/handlers/world_move.go:44-72` 接受请求体里的 `player_id` 并转发给 gRPC，没有与 JWT `sub` 比较。任何登录用户可移动任意玩家。修复：在 handler 中强制 `body.player_id == c.GetString("player_id")`。
- **P1 — 限流键可被客户端控制**：`ai-city/apps/api-gateway/internal/middleware/ratelimit.go:23-25` 优先使用 `X-Player-ID`，攻击者可换头绕过或污染他人限流桶。修复：限流键只使用已认证 `player_id` 或 ClientIP；移除对请求头的信任。
- **P2 — API 网关 JWT 未显式限定算法**：`ai-city/apps/api-gateway/internal/middleware/auth.go:25-31` 直接 `jwt.Parse`，而 `ai-city/apps/ws-gateway/internal/auth/jwt.go:40-51` 已明确 HS256。修复：抽公共 verifier 或在 keyfunc 中校验 `token.Header["alg"] == "HS256"`。
- **P2 — 前端令牌保存在 localStorage 且 WS token 走 query string**：`ai-city/web/src/lib/api.ts:118-122` 从 localStorage 恢复 token；`ai-city/web/src/lib/ws.ts:17` 拼 `${WS_URL}?token=${token}`，URL/query 更易进入日志。修复：改 httpOnly cookie 或短时 WS ticket，服务端升级后换取会话。

### 4. 性能（5.0/10）

- **P2 — Kafka 事件为 at-most-once**：`ai-city/apps/economy-service/src/economy_service/clients/kafka_producer.py:33-59` 设置 `enable_idempotence=False`，启动和发送失败只 warning，事件会丢失。资金审计虽有 DB ledger，但下游派生视图可能漏事件。修复：至少改为 producer ack + outbox 表 + 后台 relay；重要消费端做幂等。
- **P2 — 前端 fetch 没有超时/取消**：`ai-city/web/src/lib/api.ts:61` 直接 `await fetch(...)`，没有 AbortController/timeout。上游慢响应会拖住 UI 操作。修复：在 `request()` 加 5-10 秒 `AbortSignal.timeout`，区分网络超时和业务错误码。
- **P2 — WS 重连定时器未保存/清理**：`ai-city/web/src/lib/ws.ts:41-44` 在 `onclose` 里 `setTimeout` 重连，但未保存 timer，也没有 disconnect API 清理。组件卸载或主动关闭后可能反复重连。修复：保存 timer id，增加 `close()`，在 `close()` 时标记人工关闭并清 timer。
- **P2 — 中央银行性能与公平性未验证**：emit 影响所有 active wallet，`central_bank.py:70-75` 的 UPDATE 没有显式分批/锁顺序；SQL 可能随活跃用户增长变成热点。需在真实 Postgres 上压测锁等待和事务时长。

### 5. 测试与可靠性（6.5/10）

- **P1 — agent-os 当前红灯**：`uv run pytest -q` 结果为 4 failed / 331 passed / 9 skipped。失败包括无 `ANTHROPIC_API_KEY` 时未跳过的 `ai-city/apps/agent-os/tests/test_dispatcher.py:16-31`，以及 emotion schema 缺列导致的 `ai-city/apps/agent-os/tests/test_emotion_repository.py:30-84`。修复：前者加 `skipif(no key)`，后者在 CI/本地统一挂载 emotion migration；不要用 skip 掩盖 schema 漂移。
- **P1 — 迁移漂移已进入本地/CI**：`ai-city/docker-compose.yml:32` 只挂载 `pg-schema-2.0.sql`，未见 `pg-schema-2.0-emotion.sql`；该文件包含 `ADD COLUMN emotion`，见 `ai-city/packages/proto/pg-schema-2.0-emotion.sql:1-8`。修复：把 migration 编号化并全部纳入 initdb 与 CI database bootstrap。
- **P2 — 经济服务测试过度依赖 SQL 字符串 mock**：`ai-city/apps/economy-service/tests/conftest.py:29-36` 用 MagicMock 模拟 asyncpg pool，`conftest.py:80-96` 按 SQL 片段 side_effect。它无法捕获真实 SQL 拼写、约束、事务语义和 schema 变更。修复：为 purchase/transfer/emit/sink 增加 real-Postgres tests，mock 只保留给 Kafka/Redis。
- **P2 — CI 缺 typecheck 硬门禁**：CI 有 lint/test/build，见 `ai-city/.github/workflows/ci.yml:11-139`，但没有统一 `mypy`、`tsc --noEmit` 或 Go vet 步骤。修复：为 Python/TS/Go 增加类型检查 job，并先记录基线再逐步归零。
- **P2 — 安全扫描覆盖窄**：`ai-city/.github/workflows/security-scan.yml:13-33` 只构建并扫描 `apps/api-gateway`，CodeQL 未按服务矩阵标注，也未覆盖新 `economy-service`。修复：扩展 Trivy/CodeQL 到全部可部署服务，并输出服务级 report。

### 6. 开发者体验（5.0/10）

- **P2 — 状态文档互相矛盾**：`README.md:30` 写经济系统仍只是“W1 demo wallets seed”，`README.md:126` 写 `W1.4 wallets`；但 HEAD 已到 W5.4，且 `docs/15-实现状态对照.md:6` 停在 W3.2、`:53` 仍把 W3.3 当下一步。修复：以 commit/ROADMAP 生成状态，或在 PR 模板中强制同步 `README.md` + `docs/15`。
- **P2 — OpenAPI 没有生成物**：`docs/15-实现状态对照.md:55-56` 重复列为待办；API 文档仍手工维护。修复：为 FastAPI 服务加 `/openapi.json` 导出脚本，为 Go/Rust 服务从 proto/OpenAPI 单一来源生成文档。
- **P2 — 本地启动路径有隐式依赖**：`ai-city/docker-compose.yml:23` 设置 `POSTGRES_HOST_AUTH_METHOD: trust` 是为了 world-engine 手写客户端；`ai-city/apps/world-engine/src/pg_client.rs:107` 依赖该行为。新人需要读注释才知道这是本地约束。修复：在 README 运行要求中显式说明，并为生产配置提供替代 PG 客户端。
- **P3 — 文档路径/目录名与文档内容存在漂移**：`README.md:126` 的 `W1.4 wallets` 与当前 ADR/CHANGELOG/ROADMAP 的 W5.4 不一致。修复：删除历史 W-number 的重复状态，只保留当前阶段 + 链接到 source of truth。
