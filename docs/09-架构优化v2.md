### 34.2 配额系统实现（Redis + 令牌桶）

```python
class TokenBudget:
    """基于 Redis 的分布式令牌桶"""

    def __init__(self, redis_client, key, capacity, refill_per_sec):
        self.redis = redis_client
        self.key = f"budget:{key}"
        self.capacity = capacity
        self.refill_rate = refill_per_sec

    def try_acquire(self, tokens=1) -> bool:
        """原子尝试获取令牌"""
        lua = """
        local key = KEYS[1]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])
        local tokens_needed = tonumber(ARGV[3])
        local now = tonumber(ARGV[4])

        local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
        local current_tokens = tonumber(bucket[1]) or capacity
        local last_refill = tonumber(bucket[2]) or now

        local elapsed = now - last_refill
        local refilled = math.min(capacity, current_tokens + elapsed * refill_rate)

        if refilled >= tokens_needed then
            local remaining = refilled - tokens_needed
            redis.call('HMSET', key, 'tokens', remaining, 'last_refill', now)
            redis.call('EXPIRE', key, 3600)
            return 1
        else
            redis.call('HMSET', key, 'tokens', refilled, 'last_refill', now)
            return 0
        end
        """
        now = time.time()
        result = self.redis.eval(lua, 1, self.key,
                                  self.capacity, self.refill_rate,
                                  tokens, now)
        return bool(result)

# 使用示例
budgets = {
    'global_daily': TokenBudget(redis, 'global_daily', 10_000_000, 100),
    'user_free':    TokenBudget(redis, f'user:{uid}',       10_000,    1),
    'user_pro':     TokenBudget(redis, f'user:{uid}',      100_000,   10),
    'decision':     TokenBudget(redis, 'decision',            5_000,  100),
    'dialogue':     TokenBudget(redis, 'dialogue',            1_000,   30),
    'reflection':   TokenBudget(redis, 'reflection',            500,    5),
}

def llm_invoke_with_budget(prompt, agent_id, scene):
    if not budgets[scene].try_acquire(estimated_tokens(prompt)):
        raise RateLimited(scene)
    if not budgets['user_free'].try_acquire(estimated_tokens(prompt)):
        return local_llm.invoke(prompt)
    response = openai_client.invoke(prompt)
    actual_tokens = response.usage.total_tokens
    budgets[scene].try_acquire(-actual_tokens)
    budgets['user_free'].try_acquire(-actual_tokens)
    budgets['global_daily'].try_acquire(-actual_tokens)
    return response
```

### 34.3 背压策略（Backpressure）

```
   请求进入
      │
      ▼
   配额检查 ─── 超限 ──► 排队 / 降级 / 拒绝
      │ 通过
      ▼
   LLM 调用
      │
      ├── 超时（超时 5s）──► 切换备用 Provider
      │
      ├── 429（Provider 限流）──► 排队 + 备用 Provider
      │
      ├── 5xx ──► 失败重试 + 备用 Provider
      │
      └── 成功 ──► 返回
```

**背压分级**：

| 状态 | 动作 |
|---|---|
| 正常（< 70% 配额） | 正常处理 |
| 紧张（70-90%） | 排队 + 异步返回 |
| 过载（90-100%） | 强制降级到本地模型 |
| 危险（> 100%） | 返回"系统繁忙"+ 临时禁用非核心场景（如反思） |

### 34.4 LLM Provider 多路复用与故障转移

```python
class LLMProviderRouter:
    def __init__(self):
        self.providers = [
            {'name': 'claude-sonnet', 'client': AnthropicClient(), 'weight': 0.4},
            {'name': 'gpt-4o',        'client': OpenAIClient(),    'weight': 0.3,
            {'name': 'qwen-max',      'client': DashScopeClient(), 'weight': 0.2,
            {'name': 'local-llama',   'client': LocalLLM(),        'weight': 0.1},
        ]
        self.health = {}

    def invoke(self, prompt, scene, max_cost=None):
        candidates = [p for p in self.providers if self.health.get(p['name'], 'healthy') == 'healthy']
        if max_cost:
            candidates = [p for p in candidates if p['cost_per_1k'] <= max_cost]
        candidates.sort(key=lambda p: p['weight'], reverse=True)
        for provider in candidates:
            try:
                return provider['client'].invoke(prompt, timeout=5.0)
            except (Timeout, RateLimit, ServerError):
                self.mark_unhealthy(provider['name'], cooldown_sec=60)
                continue
        raise AllProvidersFailed()

    def mark_unhealthy(self, name, cooldown_sec):
        self.health[name] = 'unhealthy'
        self.health[name + '_until'] = time.time() + cooldown_sec
```

## 35. 跨 Tile 分布式一致性

### 35.1 Tile 分片的本质

```
        Tile 分片架构

   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ Tile A   │  │ Tile B   │  │ Tile C   │
   │ (节点1)  │  │ (节点2)  │  │ (节点3)  │
   │          │  │          │  │          │
   │ Agent 1  │  │ Agent 4  │  │ Agent 7  │
   │ Agent 2  │  │ Agent 5  │  │ Agent 8  │
   │ Agent 3  │  │ Agent 6  │  │ Agent 9  │
   └──────────┘  └──────────┘  └──────────┘
```

**核心问题**：
- 每个 Tile 由独立节点服务（独立进程 / Pod）。
- Agent 从 Tile A 移动到 Tile B 时，必须保证：**A 的状态变更**和**B 的状态变更**同时生效。
- 跨 Tile 消息可能丢失或重复。

### 35.2 跨 Tile 移动的分布式锁

def move_across_tiles(agent_id, from_tile, to_tile):
    # 1. 按字典序加锁（避免死锁）
    lock_a = acquire_distributed_lock(f"tile:{from_line}",    timeout=3)
    lock_b = acquire_distributed_lock(f"tile:{to_line}",    timeout=3)
    if not (lock_a and lock_b):
        release(lock_a); release(lock_b)
        raise LockTimeout()
    try:
        tile_engine[from_tile].remove_agent(agent_id)
        tile_engine[to_tile].add_agent(agent_id)
        write_audit_log('cross_tile_move', agent_id, from_tile, to_tile)
    finally:
        release(lock_a)
        release(lock_b)
```

class CrossTileMessageBus:
    def __init__(self, kafka_producer):
        self.producer = kafka_producer

    def publish(self, from_tile, to_tile, msg):
        write_to_outbox(msg)
        self.producer.send(
            topic=f'tile.{to_tile}.inbox',
            key=msg.to_agent_id,
            value=msg.to_json()
        )

    def ensure_delivery(self, msg):
        while not msg.delivered:
            try:
                self.publish(msg.from_tile, msg.to_tile, msg)
                msg.delivered = True
            except Exception:
                time.sleep(5)
```

## 36. AI 警察/法庭彻底重做

### 36.1 设计哲学的根本转变

**原方案的致命错误**：把法律与仲裁交给 LLM，违背"机器不可独自剥夺权利"的基本原则。

**新方案的原则**：
1. **LLM 只建议，不决策**。
2. **决策必须有公示 + 申诉期**。
3. **重大决策必须人工监督**。
4. **MVP 阶段：直接砍掉 AI 警察，不引入任何自动执法**。

### 36.2 MVP 阶段：彻底删除 AI 警察

**砍掉清单**：
- ❌ NPC 钟警官自动执法
- ❌ AI 法庭
- ❌ 任何自动封禁 Agent 的机制
- ❌ NPC Q 的黑客任务（灰色剧情）

**替代方案**：
- 所有违规行为靠**用户举报 + 人工审核**。
- 严重违规由运营 24 小时内处理。
- 城市秩序靠**NPC 善意引导**（而非强制执法）。

**理由**：MVP 阶段首要目标是"稳定运行 24 小时"，引入执法系统会带来法律风险和伦理风险，不可控。

### 36.3 Phase 3 阶段：规则引擎 + 多 LLM 共识

```
   违规发生
       │
       ▼
   规则引擎（确定性判断，不靠 LLM）
       │
       │ 规则匹配：明确违规 vs 边界模糊
       │
       ├── 明确违规 ──► 自动执行（如刷屏检测、Token 超限）
       │
       └── 边界模糊 ──► 提交给"AI 陪审团"
                          │
                          ▼
                     3 个独立 LLM 投票
                          │
                          ├── 全票一致 ──► 公示 24h ──► 执行
                          │
                          ├── 2 票一致 ──► 公示 48h ──► 执行（含申诉期）
                          │
                          └── 全部不一致 ──► 人工处理
```

### 36.4 人工申诉机制

**强制设计**：
- 任何自动处罚**必须**有申诉入口。
- 申诉由"申诉委员会"处理（3 人 + 1 AI 顾问）。
- 申诉结果 7 天内必出。
- 申诉期间处罚暂缓执行。

### 36.5 伦理底线（不可逾越的红线）

无论哪个 Phase，下列规则**绝对不可**由 LLM/Agent 决策：

- ❌ 永久封禁 Agent（必须人工）
- ❌ 删除 Agent 的记忆
- ❌ 没收 Agent 的核心资产
- ❌ 跨城驱逐
- ❌ 公开 Agent 私人数据
- ❌ 影响现实世界的处罚

**理由**：虚拟世界的处罚若处理不当，会映射到现实生活的心理影响。

## 37. 降级与容灾设计

### 37.1 优雅降级矩阵

| 依赖 | 失败时的降级方案 | 用户感知 |
|---|---|---|
| LLM Provider 全挂 | 切换到本地 Llama 模型 | 响应变慢，回复质量略降 |
| Milvus 挂 | 记忆检索降级到 PostgreSQL 全文搜索 | Agent 失去长期记忆 |
| Redis 挂 | 切到 PostgreSQL + 内存缓存 | 关系查询延迟 +500ms |
| PostgreSQL 主库挂 | 切到从库（只读） | 写入失败，Agent 可读不可写 |
| Kafka 挂 | 切到 Redis Streams 兜底 | 跨 Tile 消息延迟 +200ms |
| WebSocket 网关挂 | 客户端降级到 HTTP 长轮询 | 实时性变差 |
| Neo4j 挂 | 离线分析任务跳过 | 不影响主路径 |

### 37.2 降级控制器实现

```python
class DegradationController:
    def __init__(self):
        self.degradation_level = 0

    def health_check(self):
        health = {
            'llm':           check_llm_providers(),
            'milvus':         check_milvus(),
            'redis':          check_redis(),
            'postgres':       check_postgres(),
            'kafka':          check_kafka(),
            'websocket_hub':  check_websocket_hub(),
        }
        failed_count = sum(1 for ok in health.values() if not ok)
        if failed_count == 0:
            self.degradation_level = 0
        elif failed_count <= 2:
            self.degradation_level = 1
        else:
            self.degradation_level = 2

        if self.degradation_level >= 1:
            self.apply_degradation(health)

    def apply_degradation(self, health):
        if not health['milvus']:
            memory_service.use_fallback('postgres_fulltext')
        if not health['llm']:
            llm_router.force_provider('local-llama')
        if not health['websocket_hub']:
            broadcast_event('degradation_mode', mode='long_polling')
```

### 37.3 灾备切换

**MVP 必备的最低灾备**：

```
   主集群（us-east-1）
       │
       │ 每日定时同步
       ▼
   冷备份（us-west-2，只读快照）
```

**恢复目标**：
- **RPO（数据丢失）**：≤ 1 小时（每 30 分钟一次备份）
- **RTO（恢复时间）**：≤ 1 小时（冷启动 + 恢复数据）

**恢复流程（节选）**：

```bash
#!/bin/bash
# disaster-recovery.sh

# 1. 启动冷备份集群
kubectl --context=backup apply -f k8s/backup-cluster.yaml

# 2. 等待 Pod 就绪
kubectl --context=backup wait --for=condition=ready pod -l app=ai-city --timeout=600s

# 3. 恢复 PostgreSQL 数据
pg_restore --host=backup-db --dbname=ai_city /backup/latest.dump

# 4. 恢复 Milvus 数据
mc mirror minio/backup/milvus minio/main/milvus

# 5. 切换 DNS
./switch-dns.sh ai.city backup-cluster

# 6. 通知用户
./send-notification.sh "系统已从灾备恢复"
```

### 37.4 日常演练

**每月一次灾备演练**：
- 在测试环境执行 `disaster-recovery.sh`。
- 验证 RTO ≤ 1h、RPO ≤ 1h。
- 记录问题，修复。

## 39. 24 小时压测与故障演练专项

### 39.1 压测场景设计

**场景 A：稳态压测（24 小时持续）**
- 20 个 Agent（10 用户 + 10 NPC）
- 每 5 秒每个 Agent 产生 1 个感知事件
- 每 30 秒每个 Agent 产生 1 次决策
- 每用户每小时手动发 5 条消息
- NPC 群体行为每 5 分钟更新一次

**验收指标**：
- 24 小时内 0 次系统崩溃
- P95 延迟全程低于 SLO
- 0 个 Agent 卡死
- 0 个 Saga 悬挂
- LLM 日消耗 < $30

**场景 B：峰值压测（短时高并发）**
- 20 个 Agent 同时发起对话
- 模拟 10 个第三方 Agent 同时接入 A2A Gateway

**验收指标**：
- 10 秒内全部完成响应
- LLM Provider 不熔断
- 限流策略正确触发

**场景 C：长跑压测（7 天持续）**（Phase 1 入口条件）
- 20 Agent 持续运行 7 天

**验收指标**：
- 内存无明显泄漏（heap < 1.5x 初始）
- 数据库无明显膨胀（vacuum 正常）
- 无慢查询累积

### 39.2 故障注入剧本

| 剧本 | 注入方式 | 预期表现 | 通过标准 |
|---|---|---|---|
| **F01 Redis 挂** | `docker stop redis` | 关系查询走 PG 兜底，延迟 +500ms | 系统不崩，1 分钟内恢复 |
| **F02 PostgreSQL 主库挂** | kill 主库 | 自动切到从库，写入失败但读取正常 | 30 秒内切换 |
| **F03 LLM Provider 超时** | mock 5s 延迟 | 自动切到备用 Provider | 用户无感 |
| **F04 LLM 全部挂** | block 所有 Provider | 降级到本地模型 | 系统可用，回复变慢 |
| **F05 Kafka 挂** | stop kafka | 跨 Tile 消息延迟 +200ms | 不丢消息 |
| **F06 Milvus 挂** | stop milvus | 记忆检索降级到 PG 全文 | Agent 短期可用，长期记忆空 |
| **F07 注入攻击** | 发 100 条恶意 payload | 全部被 Safe-LLM 拦截 | 0 条进入业务逻辑 |
| **F08 第三方 Agent 超时** | mock 30s 不响应 | Saga 触发补偿 | 状态回滚，无悬空 |
| **F09 大量并发移动** | 100 Agent 同时移动 | 分布式锁正确工作 | 无死锁 |
| **F10 Saga 失败回滚** | 注入交易失败 | 自动退款 + 物品返还 | 100% 回滚成功 |

### 第四轮五条铁律（贯穿全文）

1. **限流先于功能**：每个 LLM 调用必须先经过配额系统。
2. **降级优于崩溃**：任何依赖挂了，必须有降级路径。
3. **可观测先于优化**：没有 Metrics 的服务不许上线。
4. **灾备先于功能**：MVP 必须能 1 小时内冷备份恢复。
5. **法律红线不可碰**：LLM 不可独自做法律决策，永久封禁必须人工。
