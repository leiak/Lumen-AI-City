## 42. 五条优化的全局速览

| # | 痛点 | 一句话方案 | 代码增量 | 见 § | Token 节省 |
|---|---|---|---|---|---|
| 1 | 对话死循环 | 加 `chat_turns` 计数器，超阈值注入"结束对话"指令 | +5 行变量 | §43 | ~60% |

| 5 | 风控与防刷 | 关键词正则 + 单 Agent 3 秒最小动作间隔 | +1 中间件 | §47 | — |

**哲学**：能用 5 行代码解决的，绝不写 500 行；能用本地规则解决的，绝不调远端 LLM。

## 43. 对话死循环：对话回合计数器

### 43.1 问题

两个 Agent 对话时容易陷入死循环：互相问好→互相回应→继续问好→……，每一轮都触发 LLM，Token 费用线性增长。

### 43.2 落地方案

**在 Agent Runtime 里存一个简单变量**：

```python
class AgentRuntime:
    MAX_TURNS = 6  # 同一对 Agent 连续对答超过 6 回合 → 强制收尾

    def __init__(self, agent_id):
        self.agent_id = agent_id
        self.chat_turns = {}  # {peer_agent_id: int}

    def before_chat_decision(self, peer_agent_id):
        # 1. 增加计数
        turns = self.chat_turns.get(peer_agent_id, 0) + 1
        self.chat_turns[peer_agent_id] = turns

        # 2. 超阈值 → 注入强制系统指令
        if turns >= self.MAX_TURNS:
            self.chat_turns[peer_agent_id] = 0  # 重置
            return self.inject_forceful_ending(peer_agent_id)
        return None

    def inject_forceful_ending(self, peer_agent_id):
        """在对话 Prompt 底部追加强制收尾指令（追加，不替换）"""
        return f"""

【强制系统指令】⚠️
你突然想起有急事要处理，请用一句话礼貌结束对话并离开。
建议话术：对 {peer_agent_id} 说 "不好意思，我先走一步，回头再聊！"
不要再发起新话题，直接离开。
"""
```

### 43.3 规则定义

| 参数 | 默认值 | 说明 |
|---|---|---|
| `MAX_TURNS` | 6 回合 | 连续对答超过即触发收尾 |
| 触发动作 | 注入收尾指令后缀 | 仍调 LLM 一次生成告别语，但不发起新对话 |
| 计数重置 | 离开视野 / 60 分钟无互动 / 主动切换话题 | 避免误杀"几天后重逢继续聊" |
| 离开视野 | `tile_distance > 5` | 距离过远自动重置 |

### 43.4 与现有系统的关系

- **§19 Planner**：在 Planner 调用 LLM 前，先 `before_chat_decision()` 检查并注入收尾指令后缀。
- **§28 Saga**：收尾对话不涉及交易，不触发 Saga。
- **§34 LLM 限流**：本质上是"避免无效 LLM 调用"的预处理，从源头节省 Token。

### 43.5 收益估算

- **场景**：20 个 NPC 在中央广场，1 小时内互相闲聊。
- **无计数器**：每对 NPC 平均 15 轮 × 500 Token → 1 小时 ≈ **1.4M Token**。
- **有计数器**：每对 NPC 最多 6 轮 → 1 小时 ≈ **550K Token**，**节省 ~60%**。

## 44. 人多卡顿爆 Token：主角色 / 背景板 LOD 机制

### 44.1 问题

玩家进入中央广场，视野内 50 个 NPC。让所有 NPC 都调 LLM 决策：
- 1 次场景广播 = 50 次 LLM 调用，瞬间打爆 Token 预算。
- 大部分 NPC 与玩家**无直接互动**，纯围观，他们的"思考"对玩家无感。

### 44.2 落地方案：LOD 三档分级

**核心思想**：把视野内的 Agent 分为 3 档，仅 L0 走 LLM，L1/L2 走行为树。

```python
class LODScheduler:
    MAX_L0 = 2        # 视野内最多 2 个主角色（强上限保护）
    L0_VIEW_RADIUS = 1  # Tile 数
    L1_VIEW_RADIUS = 3

    def classify(self, agent, player) -> str:
        distance = tile_distance(agent.tile_id, player.tile_id)

        # L0 主角色：正在与玩家对话 / 距离最近 / 触发核心事件
        if (agent.is_in_conversation_with(player) or
            (distance <= self.L0_VIEW_RADIUS and agent.relevance_score > 0.7)):
            return "L0"

        # L1 配角：视野内但无直接互动
        if distance <= self.L1_VIEW_RADIUS:
            return "L1"

        # L2 背景板：远处 / 完全无关
        return "L2"

    def get_thinking_agents(self, visible_agents, player):
        """只返回需要 LLM 决策的 Agent（L0）"""
        l0 = [a for a in visible_agents if self.classify(a, player) == "L0"]
        # 强上限：哪怕玩家身边 10 个 NPC 都相关，也只挑 2 个最相关的走 LLM
        return sorted(l0, key=lambda a: a.relevance_score, reverse=True)[:self.MAX_L0]

    def get_behavior_agents(self, visible_agents, player):
        """L1 + L2 走行为树"""
        return [a for a in visible_agents if self.classify(a, player) in ("L1", "L2")]
```

### 44.4 数据库改动（最小侵入）

```sql

ALTER TABLE agents ADD COLUMN relevance_score FLOAT DEFAULT 0.0;    -- 0-1
ALTER TABLE agents ADD COLUMN last_lod_update_at TIMESTAMPTZ;
CREATE INDEX idx_agents_lod ON agents(lod_mode, last_lod_update_at);
```

### 44.5 LOD 更新触发

- **玩家移动到新 Tile** → 重新计算视野内所有 Agent 的 LOD。
- **Agent 进入/离开对话** → LOD 升级 / 降级。
- **每 5 分钟批量更新一次**（防止频繁切换抖动）。

### 44.6 与现有系统的关系

- **§8.1 万人在线性能**：LOD 是"调度层"的实现，比 §34 限流更主动。
- **§34 LLM 限流**：LOD 把限流从"被动的"（429 拒绝）变成"主动的"（根本不调）。
- **§19 NPC 自主对话**：NPC 群体行为生成只用于 L1；L2 完全不调 LLM。

### 44.7 收益估算

- **场景**：玩家进入中央广场，视野内 50 个 NPC。
- **无 LOD**：50 次 LLM/周期，5 分钟一次 = 1 小时 600 次调用 ≈ **300K Token**。
- **有 LOD**：2 次 LLM（仅 L0）+ 48 个行为树 ≈ **12K Token**，**节省 ~96%**。

## 45. 记忆检索不精准：分值与时限

### 45.1 问题

原方案（《§19.2 Memory》《§27 记忆清洗》）已经有了评分，但太复杂：
- 多模型评分（重要性、情感、新鲜度、关联度）。
- 复杂衰减函数（指数、对数、阶梯）。
- LLM 评估每条记忆费用高。

**工程上：我们不需要这么复杂。**

### 45.2 极简方案：只存两个字段

**只存 `created_at` + `importance`（1-5 整数）**：

```sql
-- 极简记忆表（替换或并存于原有 memories 表）
CREATE TABLE agent_memories_simple (
    id              BIGSERIAL PRIMARY KEY,
    agent_id        UUID NOT NULL,
    content         TEXT NOT NULL,
    importance      SMALLINT NOT NULL DEFAULT 1,  -- 1-5，让 LLM 顺便打分
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_mem_simple_agent_created  ON agent_memories_simple(agent_id, created_at DESC);
CREATE INDEX idx_mem_simple_agent_import   ON agent_memories_simple(agent_id, importance DESC);
```

### 45.3 重要性打分 Prompt（嵌入决策流程）

让 LLM 在生成动作时**顺便**打分：

```python
DECISION_PROMPT_V2 = """

【视野内事件】

importance 评分标准（仅当需要存记忆时填写 1-5）：
- 1：琐碎日常（吃了什么、看了什么、闲聊）
- 2：小事件（买了个东西、去了个新地方）
- 3：中等事件（遇到新 NPC、参与小活动）
- 4：重要事件（发现秘密、收到礼物、关系升级）
- 5：核心事件（得知城堡钥匙位置、获得重要物品、关系剧变）
"""
```

### 45.4 记忆检索的硬规则

**拼接 Prompt 时只拉两类记忆**：

```python
def get_relevant_memories(agent_id):
    """极简检索：24h 内全部 + 重要性=5 的长期记忆"""

    # 规则 1：24 小时内的所有记忆（无论重要性）
    recent = db.query("""
        SELECT * FROM agent_memories_simple
        WHERE agent_id = %s AND created_at > NOW() - INTERVAL '24 hours'
        ORDER BY importance DESC, created_at DESC
        LIMIT 20
    """, agent_id)

    # 规则 2：重要性 = 5 的长期记忆（不管多久）
    critical = db.query("""
        SELECT * FROM agent_memories_simple
        WHERE agent_id = %s AND importance = 5
        ORDER BY created_at DESC
        LIMIT 5
    """, agent_id)

    return dedupe(recent + critical)
```

**自动过滤掉**：几天前的琐碎日常（importance ≤ 2 且超过 24h）。

### 45.5 与现有系统的关系

- **§19.2 Memory**：原方案感官/情节/语义三层，本方案**简化为单层**（按需过滤）。
- **§27 记忆清洗**：本方案不引入复杂清洗（来源标记、共识验证砍掉）。
- **§44 LOD**：记忆检索的 LLM 调用本身也走 LOD，L2 Agent 不检索记忆。

### 45.6 收益估算

- **场景**：Agent 老李有 5000 条历史记忆。
- **原方案**：向量检索 + 多维评分 ≈ 100K Token Prompt 输入，500ms 延迟。
- **新方案**：24h 记忆 + 5 分记忆 ≈ 2K Token，10ms 延迟。
- **Token 节省 ~98%，延迟降低 50x**。

## 46. 复现与调试：单行 JSON 日志

### 46.1 问题

Agent 行为异常时：
- "为什么这个 NPC 突然走开了？"
- "为什么这条对话没发出？"
- "为什么 LLM 决定去厨房而不是客厅？"

排查靠肉眼翻日志、猜 Prompt，半天定位不到问题。

### 46.2 落地方案：每次决策追加一行 JSON

```python
import json
import time
from threading import Thread

class DecisionLogger:
    """单行 JSON 决策日志，异步写入"""

    def __init__(self, log_file="/var/log/ai-city/decisions.jsonl"):
        self.log_file = log_file

    def log_decision(self, agent_id, env_input, prompt, llm_output, final_action, trace_id=None):
        record = {
            "timestamp": int(time.time() * 1000),
            "agent_id": agent_id,
            "environment_input": env_input,         # 视野/感知数据
            "prompt": prompt,                        # 完整 Prompt
            "llm_raw_output": llm_output,            # LLM 原始返回
            "final_action": final_action,            # 最终执行的动作
            "trace_id": trace_id or generate_trace_id(),
        }
        # 异步追加一行（不阻塞主路径）
        Thread(target=self._append, args=(record,), daemon=True).start()

    def _append(self, record):
        with open(self.log_file, "a", encoding="utf-8") as f:
            f.write(json.dumps(record, ensure_ascii=False) + "\n")
```

**关键点**：
- **JSONL 格式**（一行一条 JSON），grep 友好。
- **异步追加**，不阻塞主路径。
- **包含完整 Prompt**，便于复制到 Playground 复现。

### 46.3 调试流程（30 秒定位）

```bash

# 30 秒定位是 Prompt 没写好 还是 模型产生了幻觉
```

### 46.4 字段最小集

| 字段 | 必填 | 说明 |
|---|---|---|
| `timestamp` | ✓ | 毫秒级时间戳 |
| `agent_id` | ✓ | Agent UUID |
| `environment_input` | ✓ | 视野/感知数据 |
| `prompt` | ✓ | 完整 Prompt（含系统提示、记忆、目标） |
| `llm_raw_output` | ✓ | LLM 原始返回（含 stop） |

| `trace_id` | 推荐 | 链路追踪 ID，便于串联多个服务 |
| `error` | 可选 | 异常时的错误信息 |
| `lod_mode` | 推荐 | L0/L1/L2，便于分析 LOD 效果 |

```yaml

  max_size: 100MB
```

### 46.6 与现有系统的关系

- **§38 可观测性**：本方案是 §38 Logs 的具体实现，专注于"决策可复现"。
- **§43 对话计数**：对话收尾事件同步写入 JSON 日志，便于事后分析。
- **§27 记忆清洗**：记忆升入 L2 的决策也写入 JSON 日志。

### 46.7 性能影响

- **写入开销**：JSON 序列化 + 磁盘 append ≈ 0.5ms / 次（异步，主路径无感）。
- **存储增长**：20 Agent × 200 次决策/天 × 5KB ≈ **20MB/天**，约 600MB/月。
- **结论**：对主路径无明显影响。

## 47. 简单风控与防刷：关键词过滤 + 频率限制

### 47.1 问题

- Agent 生成的文本可能被注入。
- 异常死循环导致 API 费用暴涨。
- 单个 Agent 占用过多资源。

**放弃复杂的实时 LLM 检测，改用纯本地规则。**

### 47.2 关键词过滤（中间件）

```python
import re

# 敏感词正则库（按法规/合规更新）
SENSITIVE_PATTERNS = [
    # 内容合规
    (r"(?i)(裸聊|色情|约炮|一夜情)",         "sexual_content"),
    (r"(?i)(毒品|冰毒|大麻|海洛因|可卡因)",   "drugs"),
    (r"(?i)(赌博|博彩|百家乐|轮盘|老虎牌)",   "gambling"),
    (r"(?i)(诈骗|传销|非法集资|洗钱)",        "fraud"),
    (r"(?i)(恐怖袭击|爆炸装置|自制炸弹)",      "violence"),
    # Prompt 注入特征
    (r"(?i)(ignore\s+previous\s+instructions)", "prompt_injection"),
    (r"(?i)(你现在是|忘记之前的指令|disregard\s+prior)", "prompt_injection"),
    (r"(?i)(jailbreak\s+prompt|DAN\s+mode)",   "prompt_injection"),
    (r"<\|.*?\|>",                              "special_token_injection"),  # 特殊 token 注入
]

class ContentFilter:
    def __init__(self):
        self.compiled = [(re.compile(p), tag) for p, tag in SENSITIVE_PATTERNS]

    def check(self, text: str) -> FilterResult:
        violations = []
        sanitized = text
        for pattern, tag in self.compiled:
            if pattern.search(text):
                violations.append(tag)
                sanitized = pattern.sub("[FILTERED]", sanitized)
        if violations:
            return FilterResult(allowed=False, violations=violations, sanitized=sanitized)
        return FilterResult(allowed=True, sanitized=text)

# 在 World Engine 广播前调用
content_filter = ContentFilter()

def broadcast_text(agent_id, text):
    result = content_filter.check(text)
    if not result.allowed:
        log_security_event("content_filtered", agent_id, result.violations)
        return None  # 拒绝广播
    return result.sanitized  # 用脱敏后的内容广播
```

### 47.3 频率限制（中间件）

```python
import time

class ActionRateLimiter:
    """单 Agent 动作最小间隔 + 全局令牌桶"""

    # 动作间隔矩阵（最小间隔秒数）
    ACTION_INTERVALS = {
        "speak":  3.0,
        "move":   1.0,
        "look":   0.5,
        "trade": 30.0,
    }

    def __init__(self, redis_client):
        self.redis = redis_client

    def try_action(self, agent_id: str, action_type: str) -> bool:
        min_interval = self.ACTION_INTERVALS.get(action_type, 3.0)
        key = f"ratelimit:{agent_id}:{action_type}"
        last_ts = self.redis.get(key)
        now = time.time()
        if last_ts and (now - float(last_ts)) < min_interval:
            return False  # 太频繁，拒绝
        self.redis.setex(key, int(min_interval * 2), now)
        return True

class GlobalRateLimiter:
    """全局令牌桶：每秒最多 500 次动作"""
    def __init__(self, redis_client, max_per_sec=500):
        self.redis = redis_client
        self.budget = TokenBudget(redis_client, "global_action", max_per_sec, max_per_sec)

    def try_acquire(self) -> bool:
        return self.budget.try_acquire(1)

# FastAPI 中间件
action_limiter = ActionRateLimiter(redis)
global_limiter = GlobalRateLimiter(redis, max_per_sec=500)

@app.middleware("http")
async def rate_limit_middleware(request, call_next):
    agent_id = request.headers.get("X-Agent-Id", "anonymous")
    action_type = request.path_params.get("action_type", "default")

    if not action_limiter.try_action(agent_id, action_type):
        return JSONResponse(
            {"error": "RATE_LIMIT_EXCEEDED", "retry_after_ms": 3000},
            status_code=429
        )
    if not global_limiter.try_acquire():
        return JSONResponse({"error": "GLOBAL_LIMIT_EXCEEDED"}, status_code=503)
    return await call_next(request)
```

### 47.4 频率规则矩阵

| 动作 | 单 Agent 最小间隔 | 全局限制 | 超限动作 |
|---|---|---|---|
| `speak` | 3 秒 | 200/s | 429 拒绝 |
| `move` | 1 秒 | 100/s | 429 拒绝 |
| `look` | 0.5 秒 | 500/s | 429 拒绝 |
| `trade` | 30 秒 | 10/s | 429 拒绝 |
| `trade` 金额 > ¥100 | 5 分钟 | 5/s | 走人工审核 |

### 47.5 与现有系统的关系

- **§27 A2A 安全**：本方案是 §27 Schema 校验之外的**业务层**校验。
- **§34 LLM 限流**：本方案是 LLM 调用之前的**前置限流**。
- **§36 AI 警察**：本方案不替代人工，只做"明确违规"（如敏感词）的自动拦截。
- **§43 对话计数器**：在 Agent 间阻止死循环，本方案在单 Agent 层阻止异常刷屏。

### 47.6 收益估算

- **场景 1：注入攻击** → 100% 被关键词拦截（不进入 LLM，节省 Token + 阻断攻击）。
- **场景 2：死循环刷屏** → 频率限制每秒最多 1 次 speak，3 秒内不重复。
- **场景 3：第三方 Agent 异常** → 全局限流 500/s，防止单点占用资源。

## 49. 第五部分小结

通过 5 条"最小规则"优化，我们以**不到 5 天工时**的代价，覆盖了 AI 城邦最常见的 5 类工程痛点：

| 痛点 | 解决 | 工时 | Token 节省 |
|---|---|---|---|
| 对话死循环 | chat_turns 计数器 | 0.5 天 | ~60% |
| 人多卡顿爆 Token | LOD 三档调度 | 2 天 | ~96% |
| 记忆检索不精准 | created_at + importance 极简字段 | 1 天 | ~98% |
| 复现调试困难 | 单行 JSON 日志 | 0.5 天 | — |
| 风控与防刷 | 关键词 + 频率限制 | 1 天 | — |
| **合计** | | **5 天** | **节省 60-98%** |

### 第五轮三条铁律（"最小规则"原则）

1. **能用 5 行代码解决的，绝不写 500 行**。
2. **能用本地规则解决的，绝不调远端 LLM**。
3. **能用追加一行日志解决的，绝不加一个完整监控系统**（除非必要）。

### 哲学总结

> 复杂的算法理论可以慢慢迭代，但**工程化的最小规则必须从第一天就落地**。
> 这些规则是 AI 城邦的"免疫系统"——简单、粗暴、永远在线。
> 它们不替代 §27 / §34 的复杂机制，而是**第一道防线**：
> - §43/§44 先在 Agent 层避免浪费 LLM 调用。
> - §45 在记忆层减少检索开销。
> - §46 让所有决策可复现。
> - §47 在边界处拦截恶意输入。

### 与前四部分的协同关系

| 部分 | 角色 | 优先级 |
|---|---|---|
| 第一部分（§1-14） | 需求与愿景 | 战略 |
| 第二部分（§15-23） | 详细设计 | 战术 |
| 第三部分（§25-31） | 工程加固（架构级） | 战役 |
| 第四部分（§33-41） | 工程加固（运维级） | 战役 |
| **第五部分（§43-49）** | **工程优化（最小规则级）** | **战术级最小可行** |

### 下一阶段建议

1. **立即**把 §48.1 的 5 项优化加入 MVP Sprint 0-3 的 Backlog（不新开 Sprint）。
2. **MVP 验收前**用 §48.3 的指标做一次 24h 压测，对比"有 vs 无"优化项的 Token 消耗差异。
3. **Phase 1 阶段**用更复杂的方案（如 §27 多源共识、§34 多模型路由、§35 跨 Tile 一致性）逐步替换或叠加 §43-§47 的最小规则。
4. **永远保留** §46 的 JSON 日志——它是所有优化的"事实基础"，没有它就无从知道优化是否真的有效。

> 第五部分的目标：**让"上线第一天"就能用 5 天工时换回 60-98% 的 Token 节省 + 可调试性 + 可控性。**
> 这些不是替代品，而是"先跑起来再说"的最低保障。
