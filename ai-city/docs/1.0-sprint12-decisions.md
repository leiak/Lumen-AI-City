## Q1：acceptance_1_0 binary 放哪里？

### 最终决策：**`apps/a2a-gateway/cmd/acceptance_1_0/main.go`**（与现有 4 smoke 同模式）

### 理由

1. **复用现有 docker pipeline**。a2a-gateway 镜像已经 bake 了 `a2a_smoke` / `http_smoke` / `inbox_smoke` 等 4 个 smoke binary。多加一个不动镜像构建流程（不新增 Dockerfile、不动 compose build context、不引多阶段构建）
2. **shared registry 不影响 acceptance**。acceptance_1_0 不注册 a2a card，只读 world-engine / api-gateway / ws-gateway；shared state = 0 风险
3. **镜像命名 `aitown/a2a-gateway`** 不需要为 acceptance_1_0 单独建镜像

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| a2a-gateway/cmd/ ✅ | 复用构建 + shared image | a2a-gateway 实际"冻结"但仍能跑 binary | 1.0 期间 a2a-gateway 镜像仍在维护（74 测试），加一个 binary 不破"冻结"语义 |
| 新 app `acceptance-runner/` | 语义清晰 | 新 Dockerfile + compose service + 新镜像构建 | 1.0 工期紧（20d）；6 个 smoke 1 个 runner 模式已够 |
| 嵌入 `cmd/api-gateway/` | - | api-gateway 镜像只有 REST + gRPC，没有 ws dial 依赖 | acceptance_1_0 需 WS client（nhooyr.io），引到 api-gateway 镜像破坏单一职责 |
| 外部 `scripts/acceptance_1_0.sh` | 不需 Go binary | 缺 typed envelope 解析 + 重试逻辑 + hint 表 | shell 写 5 步骤 + 8.5d 太脆；Go 库（websocket / json / struct）现成 |

### 实施影响

- `apps/a2a-gateway/cmd/acceptance_1_0/main.go` 单文件（与现有 `cmd/a2a_smoke/main.go` 同结构）
- `apps/a2a-gateway/Dockerfile` 在最后 `COPY` 多 1 行 `acceptance_1_0`
- `docker-compose.yml` a2a-gateway service 加 `command: ["/app/a2a-gateway", "/app/acceptance_1_0"]` 不用改（smoke 是 exec 进镜像手动跑，不是 entrypoint）
- **不动**：a2a-gateway 业务代码、proto、registry、inbox

## Q2：玩家点 NPC 后 NPC 没主动 say 的 UX

### 最终决策：**弹 NPCDialog 但 options 为空，placeholder 文案"等 NPC 说话"，关闭按钮唯一可交互**

### 理由

1. **1.0 不做"点 NPC 主动触发 ask"协议**（plan §六 / §八.2 显式拒绝）。所以点 NPC 只是"打开对话窗口"，不能"逼 NPC 说话"
2. **dialog 不弹则玩家永远进不去** —— 即使 NPC 已 say 过，玩家也得能"再开看"
3. **options 为空 = 视觉降级**：玩家看到对话框就知道"NPC 还没说话"；提示文案再补强一次
4. **关闭按钮唯一** 是因为 1.0 不做"再触发 query"流程

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：弹空 dialog + 提示 | UX 清晰 | 玩家点了没反应可能困惑 | 提示文案"等 NPC 说话"够清晰；stakeholder demo 演示时手控节奏 |
| 不弹 dialog | 简单 | 玩家点了没反应 = 死按钮 | 必须有反馈，否则像 bug |
| 弹"打招呼" 招呼 + 选项 | 1.0 有内容 | 引入"点 NPC 主动 ask" 协议 → 1.0 不做 | plan §六 显式拒绝 |
| 等 NPC 说话 + 自动开 dialog | 0 玩家操作 | 1.0 玩家必须"等"，不能主动看历史 | 失去"再看一次对话"能力 |

### 实施影响

- NPCDialog 组件初始 state：
  ```ts
  type State =
    | { mode: 'empty'; reason: 'npc_silent' }    // 玩家点 NPC
    | { mode: 'showing'; npcId; say; options[] } // NPC 主动 say / 玩家回复后
  ```
- placeholder 文案写死："王老板在忙，等会儿再说话"（不调 API）
- 关闭按钮始终显示
- acceptance_1_0 step 4 不测此 UX（NPC say 是异步触发，stakeholder 看时间窗口）

## Q3：First-login 标记走 PG 还是内存

### 最终决策：**内存 `set[str]`（agent-os 进程内），重启丢**

### 理由

1. **1.0 demo 重启是低频事件**（每天 1-2 次），重启后再 welcome 1 次玩家影响 ≤ 30 秒的 demo 体验
2. **不引 PG 依赖**：agent-os Sprint 11 设计就不直连 PG（参 `1.0-sprint11-tasks.md`），welcome 状态不该破例
3. **stakeholder 文档明确说"demo 前先重启 agent-os 让 set 清空"** —— 单次操作可接受

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：内存 set | 0 依赖；简单 | 重启丢 | demo 节奏可接受 |
| Redis HSET | 重启不丢 | 1.0 agent-os 不用 Redis（避免多 1 协议层）；2 字符写比 set 慢 | 1.0 简化 |
| PG 表 `welcomed_players(player_id)` | 持久化 | agent-os 需直连 PG + 表迁移；+1d 工时 | 1.0 不持久化欢迎状态 |
| 接 a2a-gateway inbox 当"已读"标记 | 复用现有 | a2a-gateway 冻结；语义错位 | inbox 是消息，不是"已触发事件" |

### 实施影响

- `apps/agent-os/src/agent_os/player_listener.py::welcomed_players: set[PlayerID] = set()`
- listener tick：player_moved 进 tile_0_0 且 player_id ∉ set → 触发 welcome 剧本 + add
- 文档 `docs/CHANGELOG-1.0.md` "已知限制"段加一句："重启 agent-os 会重置 welcome set，已 welcome 玩家可能被再次 welcome；demo 前请先 restart agent-os"
- **不动**：PG schema、Redis、a2a-gateway

## Q4：王老板 talk_tree 递归深度

### 最终决策：**2 层（root → ask_X → ask_Y）**

### 理由

1. **1.0 演示时长 3min**：嵌套 3 层对话至少 4-5 次往返，超 stakeholder 注意力窗口
2. **BT 节点硬约束**：Sprint 11 BT 只有 3 节点（Sequence/Selector/Action）；复杂 tree 需扩节点 → 1.0 显式拒绝
3. **2 层足够证明"剧本可分支"**：root 5 选项 + 任意一个选项展开 3 二级选项 = 证明选择可递归

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：2 层 | 简单；3min 演示够 | 多轮复杂对话不能演示 | 1.0 不演示复杂 |
| 1 层（root 5 选项） | 最简 | 5 选项点完即终止，没"递归" 概念 | 无法证明对话树可扩展 |
| 3 层 | 接近真实游戏 | +1d 写 yaml + BT 节点要扩 | 1.0 复杂度超预算 |
| 任意深 | 灵活 | BT 要扩递归节点 + 容易写成"伪 DSL" | 1.0 永远不做 Saga DSL |

### 实施影响

- `wang_boss.yaml::talk_tree` 结构（伪）：
  ```yaml
  talk_tree:
    root: { options: [ask_business, ask_directions, ask_weather, goodbye, compliment] }
    ask_business: { reply: "...", next_options: [ask_price, ask_history, goodbye] }
    ask_price:    { reply: "...", next_options: [buy, goodbye] }      # 终止于 buy/goodbye
    ask_history:  { reply: "...", next_options: [ask_directions, ask_directions2, goodbye] }
    # ... 其他 root 选项直接终止于 goodbye
    goodbye: { reply: "...", next_options: [] }   # 终止
  ```
- 2 层 = root → leaf。leaf 的 next_options 必须为空或只剩 goodbye（不能 3 层）
- acceptance_1_0 step 5：选 `ask_business` → 验 reply 显示 3 二级选项（`ask_price` / `ask_history` / `goodbye`）

## Q5：5 选项 ID 命名约定

### 最终决策：**snake_case**（`ask_business` / `ask_directions` / `ask_weather` / `goodbye` / `compliment`）

### 理由

1. **跨语言一致性**：yaml（snake_case 自然）+ Go handler（snake_case JSON tag）+ web（TS 也常用 snake_case）三层无需做 case 转换
2. **人类可读**：`ask_business` 比 `AskBusiness` 或 `askBusiness` 都更清楚（业务/产品同学读 yaml 不需学 camelCase 习惯）
3. **避免连字符 URL 问题**：snake_case 在 URL query / path 里无歧义（vs `ask-business` 在某些框架要 percent-encode）

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：snake_case | yaml / Go / TS 一致 | TS 风格不一致（社区偏 camelCase）| 跨语言项目 snake_case 更友好；3 处风格 vs 1 处不一致 |
| camelCase | TS 友好 | Go yaml tag 要写 `askBusiness`；yaml 读起来怪 | 1 处统一不如 3 处统一 |
| kebab-case | URL 友好 | yaml 习惯用 `_`；Go 字段要写 `ask-business` json tag | 同上 |
| PascalCase | 类名风格 | 选项 ID 不是类 | 语义错 |

### 实施影响

- `wang_boss.yaml::talk_tree` key 全 snake_case
- `apps/api-gateway/internal/handlers/npc.go::request{Choice string \`json:"choice"\`}` 字段名 `choice`（单数小写），但 **option id** 不在 request 字段上，是 payload 值 —— 无强制 snake_case 校验（JSON string 即可）
- `web/src/components/NPCDialog.tsx::option.id` 直接用 yaml key
- **不动**：现有代码 / schema / 协议

## Q6：welcome 剧本 yaml 独立文件 vs wang_boss.yaml 字段

### 最终决策：**独立文件 `packages/npc-templates/wang_boss_storylines/welcome.yaml`**

### 理由

1. **关注点分离**：主模板（OCEAN/性格/常用台词/bt）和剧本（触发条件 + 步骤链）两件事不同生命周期
   - 主模板：NPC 一生基本不变
   - 剧本：1.0 期间可能改 welcome 触发条件或加 storyline
2. **2.0 替换路径清晰**：Saga DSL 替换独立 storyline 文件即可，主模板不动
3. **避免主 yaml 变胖**：主模板已 60 行；加 storyline 步骤链可能 +50 行 → 主 yaml 难读

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：独立文件 | 关注点分离；2.0 易替换 | 多 1 文件 | 1 文件不复杂；约定清晰 |
| 主 yaml `storylines:` 字段 | 1 文件搞定 | 主 yaml 胖；2.0 Saga 替换要动主 yaml | 主 yaml 是 NPC 身份，storylines 是行为 |
| 放 PG 表 | 多 NPC 共享 storyline | 1.0 不持久化对话 / 不写 PG | 复杂度超 |
| 代码硬编码 | 0 yaml | 改欢迎台词要改代码 | YAML 是 1.0 配置层规范 |

### 实施影响

- 新建 `packages/npc-templates/wang_boss_storylines/welcome.yaml`（独立文件）
- `apps/agent-os/src/agent_os/storyline.py::StorylineLoader` 扫 `packages/npc-templates/*/storylines/*.yaml`
- 主 `wang_boss.yaml` 不加字段（保持 60 行）
- **不动**：schema.json 主结构（OCEAN-schema.json 也不加 storyline 字段，storyline 文件 schema 单独建）

## Q7：Playwright 等待 NPCDialog 超时

### 最终决策：**5 秒**

### 理由

1. **acceptance_1_0 step 4 等待 NPC say 是 5s**（参 `docs/1.0-acceptance-design.md`）：web 端 5s 内能收到 envelope，dialog 必出现
2. **demo 节奏**：5s 内 NPC 不说话 = 真有问题；10s 太长，CI 卡 1 个 case 多 5s × N
3. **CI 友好**：单 case 总耗时控制在 8s 内（5s wait + 3s 操作），跑全套 4 case ≤ 40s

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：5s | 与 binary 一致；CI 友好 | 真慢 case 偶发 fail | 加 retry 1 次即覆盖偶发 |
| 3s | 更快 | 太短，walk + tick + say 跨多 boundary 易超时 | 不可靠 |
| 10s | 更稳 | +5s 单 case；与 binary 不一致（5s） | binary 都 5s，Playwright 10s 显得不一致 |
| 30s | 极稳 | CI 卡 | CI 资源宝贵 |

### 实施影响

- `web/e2e/npc-dialog.spec.ts::await expect(page.getByTestId('npc-dialog')).toBeVisible({ timeout: 5000 })`
- `package.json` Playwright project 设 `timeout: 30_000`（test-level），单 expect 设 5000
- **不写**：retry 机制（首跑偶发 +1s 重试留给手动）

## Q8：录屏时长

### 最终决策：**3 分钟**

### 理由

1. **stakeholder 注意力窗口 3-5min**：3min 跑完核心闭环刚好；超过 5min 注意力散
2. **录屏要"有节奏感"**：3min 容纳 login + walk + NPC 主动 say + 玩家回复 + 第 2 个 tab 看实时同步 + acceptance_1_0 5/5 命令 —— 每节点 30s
3. **README 顶部链接**：录屏嵌入 README，3min 文件 ≤ 5MB，GitHub 可直接预览

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：3min | 注意力窗口内；节奏紧凑 | 信息密度高，每个镜头 ≤ 30s | stakeholder 一遍看完能复述 |
| 1min | 超紧 | 缺第 2 tab 同步演示 | 缺关键演示环节 |
| 5min | 更详细 | stakeholder 注意力散；文件 > 8MB | 视频不被看完风险 |
| 10min | 极详细 | GitHub 不让传；YouTube 上传耗时 | 1.0 不要过长视频 |

### 实施影响

- 录屏脚本（28 行）参 `docs/1.0-sprint12-tasks.md` §T12a 已有
- 输出：MP4 / WebM 均可，建议 WebM（GitHub README 兼容好）
- 工具：Windows 用 Xbox Game Bar（不需装）；macOS 用 QuickTime
- README 顶部：`<video src="docs/assets/demo-1.0.webm" controls width="640"></video>`
- **不动**：CI（录屏手动做）；git LFS 不启用（< 5MB）
