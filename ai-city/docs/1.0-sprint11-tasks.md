### T02：world-engine server 加 NPC 位置数据模型（2d）

**为什么必须**：当前 world-engine 只有 `player_position` 表（PG）+ 内存 `players map`。王老板走 1 步必须有地方存他的新坐标。

### T05：BT runtime 最小版（2d）

**3 节点类型**（与原计划 5 节点差异：砍 Inverter + Condition）：

| 节点 | 语义 | 用途 |
|---|---|---|
| `Sequence` | 顺序执行子节点；全部 SUCCESS 才返 SUCCESS | 玩家进范围 → say |
| `Selector` | 试子节点；第一个 SUCCESS 即返；全 FAIL 才返 FAIL | 优先级：玩家进范围 > 时间到走 > idle |
| `Action` | 叶子节点；执行副作用（walk / say / idle）| 实际行为 |

**为什么砍 Inverter + Condition**：
- 1.0 王老板行为简单（3 个 action 串起来），不需要复杂组合
- 2.0 NPC 行为变复杂时再加，**1.0 不预留**
- 砍 2 节点省 0.5d，**符合"先把 1.0 跑通"原则**

**JSON schema**（从 YAML 加载）：
```json
{
  "type": "selector",
  "children": [
    { "type": "sequence", "children": [
        { "type": "action", "name": "check_player_in_range" },
        { "type": "action", "name": "say_greeting" }
    ]},
    { "type": "sequence", "children": [
        { "type": "action", "name": "check_time_to_walk" },
        { "type": "action", "name": "walk_one_step" }
    ]},
    { "type": "action", "name": "idle" }
  ]
}
```

**tick 语义**：
```python
def tick(node, ctx) -> Status:
    if isinstance(node, Sequence):
        for child in node.children:
            if tick(child, ctx) != SUCCESS: return FAILURE
        return SUCCESS
    elif isinstance(node, Selector):
        for child in node.children:
            if tick(child, ctx) == SUCCESS: return SUCCESS
        return FAILURE
    elif isinstance(node, Action):
        return action_handlers[node.name](ctx)  # returns SUCCESS/FAILURE
```

**Action handler 表**（Sprint 11 5 个）：
- `check_player_in_range` — 读 ctx.players_in_range，非空返 SUCCESS
- `say_greeting` — dispatch.say(template.say[random])，返 SUCCESS（实际效果是把台词给 dispatcher，dispatcher 决定打 log / publish redis）
- `check_time_to_walk` — `now - ctx.last_walk_ts > template.walk_interval_seconds` 返 SUCCESS
- `walk_one_step` — dispatcher.walk_random()，更新 ctx.last_walk_ts，返 SUCCESS
- `idle` — 返 SUCCESS（Sprint 11 不做 idle 行为，纯占位）

**验收**：
- 3 单测：Sequence 全部成功 / Selector 第一个成功 / Action 调 handler
- 1 集成测：完整 BT 跑出"say → walk → idle" 3 步

**风险**：BT 状态保存——Sprint 11 假设每 tick 重新 evaluate（无状态），Sprint 12+ 加 `RUNNING` 状态机再说

### T08：agent-os main loop（2.5d）

**核心循环**：
```python
async def agent_loop(ctx, npc_registry, bt_runtime, dispatcher):
    while not ctx.done():
        for npc in npc_registry.list_active():
            try:
                bt = npc.template.bt  # pre-loaded
                status = bt_runtime.tick(bt, npc.context)
                if status == FAILURE:
                    dispatcher.log_idle(npc)  # BT 全 FAIL → idle
            except Exception as e:
                logger.error("tick failed", npc_id=npc.id, error=str(e))
        await asyncio.sleep(cfg.tick_interval_sec)  # 1s
```

**ctx（per-NPC）**：
- `npc.id` / `npc.template` / `npc.position` / `npc.last_walk_ts` / `npc.last_say_ts` / `npc.players_in_range` (set[PlayerID])
- Sprint 11：纯内存 dict；Sprint 12 持久化（让 NPC 重启不丢状态）

**walk 行为**：
- 随机选相邻 8 方向之一（同 tile 4 边 + 对角线 4 角）
- 调 `world_client.move_entity(NPC, npc.id, new_x, new_y)`
- world-engine 接受 → Redis publish `aicity:player:moved`（payload `entity_type=NPC`）→ ws-gateway fanout → 浏览器实时看到
- 移动间隔 30s（template.walk_interval_seconds）

**验收**：
- 2 单测：tick 1 NPC BT 走通 / 异常 NPC 跳过不影响其他
- 1 集成测：起 1 假 BT + 假 dispatcher，跑 10 tick 验次数正确

**风险**：tick 异常影响其他 NPC——try/except 包住每个 NPC 的 tick，单 NPC 崩不传染

### T10：player listener（1d）

**Redis 订阅 `aicity:player:moved`**：
```python
class PlayerListener:
    async def run(self, ctx):
        sub = redis_client.subscribe("aicity:player:moved")
        async for msg in sub:
            event = parse_event(msg)
            if event.entity_type != PLAYER: continue
            for npc in npc_registry.list_active():
                if distance(npc.position, event.position) <= 100:  # 同 tile
                    npc.context.players_in_range.add(event.player_id)
                else:
                    npc.context.players_in_range.discard(event.player_id)
```

**关键点**：
- listener 维护 `players_in_range` set（per NPC）
- loop tick 时 `check_player_in_range` action 读这个 set
- 玩家离开时主动 discard（避免 stale）
- 玩家 disconnected 不通知 → set 慢慢漂移 → Sprint 12 加重连清空

**验收**：1 单测（喂 fake Redis stream，验 set 更新）

**风险**：player_listener 与 agent_loop 在同一进程——listener 写 `npc.context.players_in_range`，loop 读；都在单 asyncio 任务里跑，无需锁

## 五、风险与拒绝清单

### 5.1 Sprint 11 自身风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| world-engine 改 Move handler 回归 | Move 玩家功能坏 | T02 单测覆盖 PLAYER 路径不变；现有 grpc_smoke 跑过 |
| agent-os Python 性能不够 | 5 NPC × 1s tick × BT eval = 5 BT/s —— 1.0 量级 < 1 BT/s/NPC，Python 完全够 | 1.0 不优化；2.0 100 NPC 时再考虑 |
| tick 抖动（asyncio.sleep 不准）| 王老板走 30s ± 2s 漂移 | 可接受；Sprint 12+ 加 monotonic time 校准 |
| player_listener 漏消息 | 玩家进 tile 但 NPC 不知 | Redis subscribe 不断重连；漏的消息下次 player_moved 还会触发 |
| 王老板随机走走出 tile 边界 | 走到 (-150, -150) 之外 | walk_one_step 必须 clamp 到 world 边界；T07 world_client 验 |
| 多 NPC 抢同一 tile | 王老板和李婶都到 tile_0_0 | 1.0 接受；Sprint 12 不用场景；2.0 NPC 间互斥再说 |
| 王老板的 5 个 NPC 怎么不互相干扰 | Sprint 11 只 enable 王老板 | npc_registry 默认从 PG 读所有 NPC；王老板 template 标 `enabled: true`，其他 4 个标 `false` |

### 5.2 Sprint 11 显式拒绝的"看起来该做但实际不在范围"工作

> 这些会反复被问，每次都用这一节回。

- "为什么不让 5 NPC 都动？" → 答：1.0 demo 只需要 1 NPC；多 NPC 是 2.0
- "为什么王老板不接 LLM？" → 答：1.0 不接 LLM（已定）
- "为什么不做 idle 行为？" → 答：idle = "什么都不做"；占位即可
- "为什么 BT 砍 2 节点？" → 答：1.0 行为简单；2.0 加 Inverter + Condition
- "为什么 player listener 不持久化 players_in_range？" → 答：Sprint 11 接受重启漂移；Sprint 12 加重连清空
- "为什么 NPC 位置不走 npc-templates 而走 PG？" → 答：NPC 位置运行时变（王老板会走），template 是配置；两者解耦
- "为什么 walk 模式用 random 不写状态机？" → 答：1.0 王老板不会按日程走；Sprint 12+ 不需要；2.0 加 schedule
- "为什么 T08 dispatcher 不接 WS 推送？" → 答：Sprint 12 才接 npc_dialogue；Sprint 11 say 只打 log
- "为什么不做 NPC 之间的对话？" → 答：不在 1.0
- "为什么不做战斗 / 移动碰撞？" → 答：不在 1.0
