# acceptance_1_0 接口设计

> **目的**：定义 Sprint 12 末尾要交付的 `cmd/acceptance_1_0` 二进制，让 stakeholder 5min 内能跑完"login → walk → NPC 接近 → 主动 say → 玩家回复"全流程，并得到一个 0/1 退出码作为 1.0 Definition of Done 的最终判据。
>
> **核心约束**：必须**确定性**（无 timing flake）、**自洽**（不动现有测试）、**bake 进镜像**（docker compose exec 即跑）。

---

## 〇、为什么需要单独设计这一步

`a2a_smoke` / `http_smoke` / `inbox_smoke` / `ws_smoke` 这 4 个 smoke 都是**单服务冒烟**：验 1 个服务的契约。1.0 acceptance 必须**跨 8 个服务**（postgres / redis / world-engine / api-gateway / ws-gateway / web / a2a-gateway 冻结 + **agent-os 1.0 新增**），验证的是"AI 公民 + 玩家 + 地图"这个**最小闭环**。

跨服务测试的设计点：
- 状态复位（demo 玩家位置、NPC 位置）怎么保证确定性
- 异步 NPC 行为怎么等（agent-os tick loop 不是请求-响应）
- 多频道 WS 事件怎么消费（`player_moved` + `npc_dialogue`）
- 失败时怎么诊断（log + 哪一步 + 哪条 assertion）

## 一、Binary 位置与构建

| 项 | 选择 | 理由 |
|---|---|---|
| 路径 | `apps/a2a-gateway/cmd/acceptance_1_0/main.go` | a2a-gateway 已有 4 个 smoke binary 模式（a2a_smoke / http_smoke / inbox_smoke），复用同一套 Dockerfile 模板 + Go 1.23 toolchain；不新建独立 app |
| 命名 | `acceptance_1_0`（连字符在 Go binary 名里转下划线） | 与其它 smoke 命名风格一致 |
| 大小估算 | ~400-500 行 Go | 5 步 × 80-100 行/步 + 共享 helper + CLI 解析 |
| 依赖 | 标准库 + 现有 `packages/sdk-go`（HTTP 客户端）+ `nhooyr.io/websocket`（已有）| 不引新外部依赖 |
| 镜像集成 | bake 进 a2a-gateway 镜像 | 与现有 4 个 smoke 共用；运行时 `docker compose exec -T a2a-gateway /app/acceptance_1_0` |

**为什么不放新 app**：
- 1.0 acceptance 是**测试**而非产品服务；放独立 app 会污染 apps/ 目录（已经有 10 个 stub）
- a2a-gateway 已经是 1.0 冻结的服务；acceptance_1_0 用它的工具链是合理的
- 2027 年如果 a2a-gateway deprecated，acceptance_1_0 跟着退役（与 1.0 同生命周期）

## 二、CLI 接口

```
docker compose exec -T a2a-gateway /app/acceptance_1_0 [flags]

Flags:
  -api-url string       api-gateway URL (default "http://api-gateway:8080")
  -ws-url string        ws-gateway URL (default "ws://ws-gateway:8082")
  -user string          test username (default "demo")
  -password string      test password (default "demo123")
  -npc string           target NPC id (default "npc_wang_boss_001")
  -tile string          target tile id (default "tile_0_0")
  -timeout duration     per-step timeout (default 30s)
  -reset-state          force-reset demo to known position before run (default true)
  -verbose              print full HTTP/WS traces (default false)
  -keep-alive           don't close WS on success (default false; for debug)
  -v                    print binary version + exit 0

Exit codes:
  0  all 5 steps PASS
  1  at least one step FAIL
  2  setup FAIL (DB unreachable / login fails)
  3  bad CLI args
```

**关键 flag**：
- `-reset-state` 默认开：测试开始前把 demo 玩家重置到 tile_-1_0 (50,50)，把目标 NPC 重置到 tile_0_0 (50,50)，保证确定性
- `-keep-alive` 默认关：成功后立即关 WS；如果打开则保持连接，让 stakeholder 看到推送

## 三、5 步契约

> 每步明确：输入、HTTP/WS 调用、断言、超时、失败诊断信息。

### 准备阶段（不计入 5 步）

```
0a. POST /v1/auth/login  →  拿 token + player_id + 起始位置
0b. websocket.Dial("ws://ws-gateway:8082/ws?token=...")  →  启动读 envelope 协程
0c. POST /v1/players/:id/position  →  把 demo 移到 tile_-1_0 (50,50)
0d. POST /v1/npc/:npc/position     →  把王老板移到 tile_0_0 (50,50)  ←  1.0 新增 endpoint
0e. 等 1s  →  让 agent-os tick 完 1 轮，NPC 不会乱动
```

**关键设计 — NPC 位置重置 endpoint**：
- 当前 `/v1/players/:id/position` 走 world-engine gRPC
- NPC 位置重置需要 1.0 新增 `/v1/npc/:id/position`（同样走 world-engine gRPC NPC 实体）
- 这是 1.0 的**最小新增 endpoint**，不在原计划里，必须 Sprint 12 补
- 命名上故意用 `position`（GET 触发瞬移）而非 `move`（玩家行为），区分 admin 操作和玩家行为

### 步骤 1：login

```
Input:   user=demo password=demo123
HTTP:    POST /v1/auth/login
Expect:  200, body.token 非空，body.player_id 是 UUID，body.tile_id == "tile_-1_0" 或 "tile_0_0"（demo 起始位置）
Assert:  token 长度 > 100 (HS256 3 段 base64)；player_id 匹配 UUID 格式
Timeout: 5s
Fail诊断: "step 1 login: HTTP %d body=%s"
```

### 步骤 2：walk

```
Input:   token + player_id + target=(150, 50)  →  移到 tile_1_0
HTTP:    POST /v1/world/move
Expect:  200, body.x ≈ 150, body.y ≈ 50, body.tile_id == "tile_1_0"
WS:     （已启动读 envelope 协程）5s 内收到 envelope:
        {
          "type": "player_moved",
          "trace_id": "uuid",
          "ts_ms": ...,
          "payload": { "player_id": <我的id>, "tile_id": "tile_1_0", "x": 150, "y": 50, "ts_ms": ... }
        }
Assert:  HTTP 200 + WS envelope received + payload.player_id 一致 + payload.tile_id 正确 + 浮点容差 < 0.01
Timeout: 5s
Fail诊断: "step 2 walk: http_code=%d ws_received=%v payload=%+v"
```

**关键设计 — WS envelope filter**：
- 启动时只关心 `type == "player_moved"` 和 `type == "npc_dialogue"` 两种
- 其它 type（未来的 `npc_moved` / 系统通知）一律忽略但记录 log
- 用 channel 缓冲 + select，不阻塞 WS 读循环

### 步骤 3：NPC 接近

```
Input:   token + player_id
HTTP:    POST /v1/world/move  →  移到 tile_0_0 (50, 50)  ←  王老板所在 tile
Expect:  200, body.tile_id == "tile_0_0"
等待:    让 agent-os tick 完一轮（≤ 1 tick 间隔 = 1s）
Assert:  GET /v1/tiles  →  body 中 tile_0_0.player_ids 包含 player_id，tile_0_0.npc_ids 包含 wang_boss_001
Timeout: 5s
Fail诊断: "step 3 npc_approach: tile_0_0.players=%v npcs=%v"
```

**关键设计 — 玩家走回 tile_0_0 而不是让 NPC 走过来**：
- 1.0 NPC 行为简单（脚本化"玩家进 1 tile 范围内 → say"），不必验证 NPC 主动寻路
- 玩家主动走近，更稳定，更能体现"NPC 反应"
- 节省 agent-os 状态机复杂度

### 步骤 4：NPC 主动 say

```
等待:    agent-os tick（≤ 1s）→ 触发王老板 say 行为 → Redis publish aicity:npc_dialogue
WS:     5s 内收到 envelope:
        {
          "type": "npc_dialogue",
          "trace_id": "uuid",
          "ts_ms": ...,
          "payload": {
            "npc_id": "npc_wang_boss_001",
            "player_id": <我的id>,
            "tile_id": "tile_0_0",
            "say": "欢迎来到城邦！有什么可以帮你的吗？",
            "talk_tree": [
              { "id": "ask_business", "text": "老板你这卖什么？" },
              { "id": "ask_directions", "text": "城邦哪里好玩？" },
              { "id": "ask_weather", "text": "今天天气怎么样？" },
              { "id": "goodbye", "text": "我先走了" },
              { "id": "compliment", "text": "你看起来真精神" }
            ]
          }
        }
Assert:  envelope.type == "npc_dialogue" + payload.npc_id 一致 + payload.say 非空 + talk_tree 长度 == 5
Timeout: 5s（含 agent-os tick 1s + Redis publish 100ms + WS 推送 50ms + 容差）
Fail诊断: "step 4 npc_say: ws_frames=%v (looking for npc_dialogue)"
```

**关键设计 — 频道 `aicity:npc_dialogue` 接入 ws-gateway**：
- 这是 1.0 的**第 2 个频道**（Sprint 10 已经为多频道铺路）
- ws-gateway.subscribe(`aicity:player:moved`, `aicity:npc_dialogue`)  ← 1.0 main.go 配置加 `REDIS_CHANNELS=...`
- envelope type 按 Sprint 10 约定从频道名剥前缀：`aicity:npc_dialogue` → `npc_dialogue`
- web 前端需要处理这个新 type（弹 NPCDialog 气泡），但 web 端改动不在 acceptance_1_0 范围 —— acceptance_1_0 直接验 WS 帧

### 步骤 5：玩家回复

```
Input:   token + npc_id + choice="ask_business"
HTTP:    POST /v1/npc/:npc_id/talk  ←  1.0 新增 endpoint
         body: { "choice": "ask_business", "player_id": <我的id> }
Expect:  200, body.reply 非空，body.next_options == null 或空（对话结束）
Assert:  HTTP 200 + body.reply 包含 "王老板" 相关词（"好酒"/"王记"/"镇店" 任一）
Timeout: 5s
Fail诊断: "step 5 player_reply: http_code=%d body=%s"
Fail诊断（缺 endpoint）: "step 5 player_reply: POST /v1/npc/.../talk 404 — endpoint not implemented (1.0 MUST)"
```

**关键设计 — `POST /v1/npc/:id/talk` 是 1.0 必须 endpoint**：
- 不在原计划里
- 必须 Sprint 12 实现
- 走 api-gateway handler → 读 npc-templates 对应 talk_tree.choice → 拿 reply
- 无 LLM，纯脚本查表
- 失败诊断信息特意写明 "1.0 MUST" 让 implementer 看到立刻知道必须做

### 步骤 5 后清理（不算步骤）

```
- close WS 连接（除非 -keep-alive）
- log: "[OK] all 5 acceptance_1_0 checks passed"
- exit 0
```

## 四、时序模型与超时

### 4.1 总时间预算

```
准备阶段：~2s  (login + WS connect + reset demo + reset NPC)
步骤 1：  1s   (login 验证)
步骤 2：  1s   (move + WS 收 frame)
步骤 3：  1.5s (move + tick 1s + GET /v1/tiles)
步骤 4：  1.5s (tick 1s + npc_say + WS 收 frame)
步骤 5：  1s   (POST /v1/npc/.../talk)
清理：    0.5s
合计：    8.5s （理想情况）
```

`timeout` flag 默认 30s（每个步骤上限）；CI 跑总时长 < 15s；stakeholder 手动跑 < 30s。

### 4.2 并发模型

```
主 goroutine：
  - 跑 5 步串行
  - 每步等 WS 收 envelope 时用 select + timer

WS 读 goroutine（启动后一直跑）：
  - nhooyr Read 循环
  - 每条 message 解析 envelope → 投到 channel
  - 主 goroutine 用带超时的 select 从 channel 取

agent-os 端（不在 acceptance_1_0 控制）：
  - tick 间隔 1s
  - 玩家进 NPC 1 tile 范围 → 触发 say → publish aicity:npc_dialogue
```

**关键设计 — WS 读 goroutine 全程在线**：
- 不能用 receive-once 模式（步骤 2 收一次就关，下一步要重连）
- 5 步全程用同一个 WS 连接
- 失败时关掉，正常完成时也关掉（除非 -keep-alive）

### 4.3 确定性保证

| 不确定源 | 缓解 |
|---|---|
| 玩家位置漂移（上轮跑残留） | `-reset-state=true` 强制重置 demo 到 (50,50) |
| NPC 位置漂移 | reset NPC 到 tile_0_0 (50,50) |
| agent-os tick 抖动 | wait >= 1 tick 间隔（最多 1.1s 抖动可忽略） |
| WS 推送慢 | 步骤 4 timeout 5s 容忍 50ms 推送延迟 |
| NPC 行为不触发 | 检查 step 3 玩家确实在 NPC tile；agent-os 端走 BT 行为树，5 步必触发 say |
| Redis 抖动 | publish 后端用现有 RedisPub 异步发布，失败仅 warn；不阻塞 server tick |

## 五、失败诊断格式

每步固定格式输出，让 stakeholder 看到错误立刻知道哪步、哪条、什么原因：

```
[FAIL] step 4 npc_say: ws_frames_received=2 (player_moved, player_moved) — no npc_dialogue in 5s
   hint: agent-os tick 正常但未触发 say 行为；检查 npc-templates/wang_boss.yaml 的 trigger 字段
   hint: 或检查 ws-gateway 是否订阅了 aicity:npc_dialogue 频道（REDIS_CHANNELS env）
   hint: 或检查 agent-os 是否真在订阅 player_moved
```

每步失败都附 **hint**（最多 3 行），根据失败模式自动选 hint。这是 acceptance_1_0 的核心价值——**让 stakeholder 5min 看到 fail 立刻能 fix**。

**hint 来源表**（hardcode 在 binary 里，不需要查文档）：

| step | 失败模式 | hint |
|---|---|---|
| 1 | HTTP 401 | "demo 用户未 seed；docker compose down -v 后 up 重建 initdb" |
| 1 | HTTP 5xx | "api-gateway 未起来或 DB 不可达；docker compose ps" |
| 2 | HTTP 200 但 WS 没 frame | "ws-gateway 未订阅 aicity:player:moved；查 REDIS_CHANNELS env" |
| 2 | HTTP 4xx | "token 失效或 player_id 不匹配；重跑" |
| 3 | tile_0_0 没 player | "demo 移到错误 tile；-verbose 看 HTTP body" |
| 3 | tile_0_0 没 npc | "王老板没 seed；docker compose down -v 后 up" |
| 4 | WS 收到但不是 npc_dialogue | "agent-os tick 正常但未触发 say；查 npc-templates 触发条件" |
| 4 | WS 收不到 | "agent-os 不在 tick；docker compose logs agent-os" |
| 5 | HTTP 404 | "POST /v1/npc/.../talk 未实现（1.0 MUST）" |
| 5 | HTTP 200 但 reply 为空 | "npc-templates 缺 talk_tree 字段或 choice 不匹配" |

## 六、Exit Code 与 CI 集成

| Exit | 含义 | CI 行为 |
|---|---|---|
| 0 | 5/5 PASS | 绿灯，merge 准入 |
| 1 | 步骤失败 | 红叉 + log；发 PR 评论自动贴失败步骤 + hint |
| 2 | setup 失败（login / DB 不可达） | 红叉 + log；通常是 infra 问题不是代码问题 |
| 3 | bad CLI args | 立刻 fail（不是测试失败） |

**CI workflow**（在 `.github/workflows/ci.yml` 加一个 job）：

```yaml
acceptance-1-0:
  needs: [lint, test, build]
  runs-on: ubuntu-latest
  services:
    # 同 §Ⅵ.2 dev-ci.yml 的 service 块（postgres + redis + world-engine + ...）
  steps:
    - uses: actions/checkout@v4
    - run: docker compose up -d --build
    - run: |
        # 等所有 8 容器 healthy
        for i in {1..60}; do
          if docker compose ps | grep -q "(healthy)" && [ "$(docker compose ps | grep -c healthy)" = "8" ]; then
            break
          fi
          sleep 2
        done
    - run: docker compose exec -T a2a-gateway /app/acceptance_1_0 -timeout 30s
```

> CI 集成不在 Sprint 12 范围。Sprint 12 只交付 binary + 本地通过；Sprint 13（或 GA 前）加 CI。

## 七、必需的 1.0 新增 endpoint

acceptance_1_0 跑通需要 2 个**不在原计划的 endpoint**：

| Endpoint | 用途 | 必须程度 |
|---|---|---|
| `POST /v1/npc/:id/position` | NPC 位置重置（admin / test 工具）| **MUST**（准备阶段必需）|
| `POST /v1/npc/:id/talk` | 玩家点 NPC 选回复 | **MUST**（步骤 5 必需）|

两个都是 1.0 范围内的 endpoint（服务于"测试"和"玩家点 NPC 互动"），不是测试专用的 hack：
- `/position` 同时给 admin 工具用（运营调整 NPC 位置 / 测试场景）
- `/talk` 1.0 web 端 NPCDialog 弹气泡时也调

**实现路径**：
- `/position`：api-gateway handler → world-engine gRPC NPC 实体（需要 world-engine 加 NPC 实体 gRPC 方法，或复用现有 Move 但传 npc_id）→ PG 写 npc_position
- `/talk`：api-gateway handler → 读 npc-templates → 查 talk_tree.choice → 返 reply（纯文件读，无 LLM）

**风险 — world-engine 加 NPC 实体 gRPC**：
- 当前 world-engine `Move` RPC 接受 player_id
- 扩到支持 npc_id 需要 proto 加 `entity_type` 枚举 + server 端 dispatch
- 1.0 最小代价：proto 加 enum + Rust 端 match + 现有 Move handler 复用
- **不引入新 RPC**
