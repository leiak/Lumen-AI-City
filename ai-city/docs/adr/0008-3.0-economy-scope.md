# ADR-0008: 3.0 经济系统 — 双货币 + 中央银行 + Redis/Kafka

**Status:** Accepted (2026-10-07)
**Date:** 2026-10-07
**Deciders:** fang, AI city core team
**Supersedes:** 无（首个 3.0 ADR；建立 3.0 经济系统范围）
**前置依赖:**
- [ADR-0007](0007-2.0-scope-llm-federation-memory-saga.md) **Accepted**（2.0 桶 1/桶 2 + 阶段 2/3 B1/B2/Phase A/B/C 已 GA；3.0 = 商业化起点）
- [ADR-0006](0006-1.0-scope-mvp-demo-slice.md) **Accepted**（1.0 MVP Demo 闭环）
**影响范围:**
- 新服务: `apps/economy-service`（FastAPI + asyncpg + redis-py + aiokafka，端口 8005）
- 新增 PG 表: `wallet` / `transaction` / `product` / `central_bank_ledger`（mount slot 07）
- agent-os BT action: 新增 `npc_sell_to_player`（5 → 6 entries）
- agent-os dispatcher: post-hook opt-in（env `BT_POST_HOOK_ENABLED` + kwarg `enable_bt_post_hook`）
- docker-compose: 新增 `economy-service` 容器（连 pg + redis + kafka）

---

## Context

3.0 引入虚拟经济系统以驱动 NPC 商品交易、玩家间转账、动态通胀模型，让"AI 公民"形成真实消费闭环。

2.0 阶段 3 已 GA（OCEAN→emotion / Saga viz / BT 编辑器），但**缺少经济闭环** — NPC 没有货币，玩家无法购买。1.0/2.0 的 demo 给 stakeholder 看完会问"AI 公民能买卖东西吗？答不能 = 商业模式无法落地"。

**3.0 v1 范围** = 最小可演示经济闭环：双货币 + 钱包 + 转账 + 商品目录 + NPC 售货 + 中央银行发钞 + Kafka/Redis。

**3.0 v1 拒绝** = 创作者市场 / 合规 / 移动端 / 多语言 / 跨城金币 / 货币兑换 / 衍生品（详见 §YAGNI）。

---

## Decision

3.0 v1 = 经济系统最小闭环的 8 项能力：

### 1. 双货币

- **gold**（金币）：玩家间转账 + NPC 商品购买
- **token**（代币）：任务产出（v1 暂未接入任务系统，仅表结构预留）
- **不互换**：gold ↔ token 不可兑换（v2 接 3.0 子轨道 #2 创作者市场）

### 2. 钱包 + 转账 + 玩家交易历史

- `GET /api/v1/wallet/{user_id}` — 查余额（Redis cache → PG fallback）
- `POST /api/v1/wallet/transfer` — 玩家间转账（`SELECT FOR UPDATE` 原子扣款 + 防双花）
- `GET /api/v1/transactions/{user_id}` — 交易历史分页（append-only transaction 表）
- **append-only transaction 表 + balance_after 快照**：审计 + 回溯不需要 rebalance；PG trigger 阻止 UPDATE/DELETE

### 3. NPC 商品目录 + 玩家购买

- `POST /api/v1/wallet/purchase` — 玩家购买 NPC 商品（`SELECT FOR UPDATE` + stock-1）
- `GET /api/v1/products` — 商品列表
- 5 NPC 各 1 商品（snack / walther / float_token / think_token / dance_token，参考 2.0 seed）

### 4. 中央银行发钞 + NPC sink（动态通胀模型）

- asyncio scheduler（embedded in economy-service）每 6 小时跑 1 次发钞
- 反通胀公式：`emit_amount = base_emit * (1 - total_supply / MAX_TOTAL_GOLD)`（总金币越接近上限，发得越少，防止 inflation bug 溢出）
- `MAX_GOLD_PER_PLAYER = 100000` 硬上限（双层防护：发钞上限 + 单玩家上限）
- NPC 商品销售触发 **sink**（金币从玩家转入中央银行 ledger 回收）
- `POST /api/v1/admin/central-bank/emit` + `POST /api/v1/admin/central-bank/sink` 手动触发（admin auth）

### 5. Kafka 3 topic（fire-and-forget）

- `econ.tx.completed` — 玩家间转账 / NPC 购买完成
- `econ.gold.emitted` — 中央银行发钞
- `econ.gold.sunk` — NPC sink 回笼
- aiokafka producer；失败仅记日志，不阻塞事务（v1 best-effort）

### 6. Redis 余额缓存

- key: `econ:{user_id}:{gold,token}`，TTL 1h
- **写时双写**（PG 提交后 partial-update Redis：`cache_balance(user_id, gold=..., token=...)` 只 SET 改过的维度）
- Redis 是 read-cache，PG 是 source of truth（缓存丢失/不一致时查 PG）

### 7. agent-os BT action `npc_sell_to_player`

- 新增 BT action entry（5 → 6 entries：say_to_player / move_to_tile / wait / set_npc_state / noop → 加 npc_sell_to_player）
- `tick()` 求值时通过 HTTP POST 调用 economy-service `/api/v1/wallet/purchase`（asyncio.to_thread 包装同步 action 防止阻塞事件循环）

### 8. dispatcher post-hook（流式完后 fire-and-forget）

- `dispatcher.say_stream()` 完成后 fire-and-forget 触发 BT action
- **opt-in**：env `BT_POST_HOOK_ENABLED=false`（默认关闭）+ kwarg `enable_bt_post_hook=False`（默认开启）
- 失败仅记日志，不影响 LLM 流式响应（不影响 1.0/2.0 行为）

## 显式不做（v1 YAGNI）

> 这些会反复被问，每次都用这一节回。

- ❌ **创作者市场 / 分成**（v2 接 3.0 子轨道 #2）
- ❌ **PIPL/GDPR 合规**（v1 不接数据导出，GA 前 4 周再做）
- ❌ **移动端钱包 UI**（仅 web 端）
- ❌ **多语言货币**（仅中文）
- ❌ **跨城金币转账**（v2 通过 a2a-gateway 协议扩展）
- ❌ **货币兑换**（gold ↔ token 不可互换）
- ❌ **衍生品 / 拍卖 / 担保交易**（商业模式未定义）
- ❌ **token 任务系统接入**（v1 表结构预留，task-service 后接）

## 关键设计决策

1. **append-only transaction 表 + balance_after 快照**：审计 + 回溯不需要 rebalance；PG trigger 阻止 UPDATE/DELETE（防止 audit log 被改）
3. **MAX_GOLD_PER_PLAYER = 100000 硬上限**：防 inflation bug 导致金币溢出（双层防护：单玩家上限 + 总上限反通胀公式）
4. **Redis 是 read-cache，PG 是 source of truth**：写时双写（`cache_balance` 仅 SET 改过的维度，partial-update kwargs 防止覆盖其他维度）
5. **Kafka fire-and-forget**：失败仅记日志，不阻塞事务；`create_task()` 真正异步；observability 监控 lag（v2）
6. **agent-os BT action 异步化**：`asyncio.to_thread` 包装同步 HTTP action，不阻塞事件循环（BT stream open + 100 frame buffer 重试沿用 2.0 阶段 2 架构）
7. **dispatcher post-hook opt-in**：env `BT_POST_HOOK_ENABLED` + kwarg `enable_bt_post_hook`，默认关闭保 1.0/2.0 行为；kwarg 优先级 > env（测试友好）

---

## 风险

| 风险 | 缓解 |
|---|---|
| 中央银行发钞 bug 导致金币无限膨胀 | MAX_GOLD_PER_PLAYER 上限 + 反通胀公式有界（不可能溢出） |
| 并发双花（同一笔钱同时被多倍消费）| PG `SELECT FOR UPDATE` + append-only transaction 表（每笔交易唯一 row） |
| Kafka producer 失败 | fire-and-forget + observability 监控 lag；事务不阻塞 |
| Redis 缓存与 PG 不一致 | Redis 是 read-cache，PG 是 source of truth；TTL 1h 自然衰减 |
| BT action 阻塞 LLM 流式 | asyncio.to_thread + fire-and-forget；失败仅记日志 |
| admin sink 接口被未授权访问 | `secrets.compare_digest` 防 timing attack + pydantic body 验证 |
| 跨城金币转账 | a2a-gateway 协议扩展（v2 候选）|
| 中央银行 scheduler 漏跑 | observability 监控 `central_bank_emit_count{}` 时间序列无 gap |
| `cache_balance` 覆盖其他维度 | partial-update kwargs：仅 SET 传入的字段（gold / token）|

---

## Consequences

### Positive

- **完整经济闭环**：NPC 商品 → 玩家消费 → 中央银行发钞 → 反通胀
- **Kafka 事件流支持 observability / Saga 后续扩展**（3 topic emit）
- **Redis 缓存降低 wallet 读取 latency**（TTL 1h 双写）
- **agent-os BT 集成让 NPC 主动售货**（不只是被动对话）
- **append-only 审计**：交易历史不可改，合规前置
- **反通胀公式 + 硬上限**：数学上不可能金币溢出（双层防护）

### Negative

- **双服务耦合**：economy-service + agent-os BT action（dispatcher post-hook 触发）
- **中央银行 scheduler 需要 observability 监控漏跑**（v1 暂未接 prometheus）
- **Kafka 事件 schema 是 best-effort**（v1 不强制订阅，v2 接 Saga 引擎）
- **append-only 阻止 UPDATE/DELETE**：审计 OK，但客服手动改余额需要走 admin path（PG trigger 必须 bypass）

### Trade-offs

- **append-only vs 可改**：选 append-only（审计 + 防作弊）；客服工具 v2 接 3.0 子轨道 #2
- **Redis 双写 vs single source**：选 Redis 双写（latency -50ms）；接受最终一致（1h TTL）
- **Kafka fire-and-forget vs 强一致**：选 fire-and-forget（不阻塞事务）；v2 接 Saga 时升级为 outbox 模式

### 成功判据（stakeholder 视角）

stakeholder 走完 3.0 演示时能向同事复述 3 件事：

1. **"NPC 玩家能用金币买商品，库存会自动 -1。"**（商品目录 + 购买）
2. **"玩家间可以转账，余额秒到，且交易历史能查。"**（转账 + 交易历史）
3. **"中央银行会自动发钞，但永远不会金币溢出。"**（反通胀公式 + 硬上限）

如果只能记 1 件 → **金币硬上限**（3.0 v1 最差异化 = 经济安全保证）。
