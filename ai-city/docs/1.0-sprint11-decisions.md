## Q1：world-engine MoveEntity 用 enum 复用还是新增 RPC

### 最终决策：**enum 复用 — 在现有 `Move(MoveRequest) → MoveResponse` 加 `EntityType` enum + `entity_id` 字段**

### 理由

1. **proto 增量最小**：`MoveRequest` 加 1 字段 + 加 1 enum；不动 message 序号；不动 RPC 序号；现有 client 兼容（default = PLAYER）
2. **server 端逻辑复用**：现有 Move handler 加 1 个 `match entity_type` 分支；不动 service trait
3. **proto 不动产物**：Sprint 12 acceptance_1_0 binary 调用 Move RPC 不破
4. **T01 工时最小**：0.5d 即可（参 Sprint 11 §三 T01）

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：enum 复用 Move | proto 增量小；client 兼容 | server 要 match EntityType | 1 处 server 分支 vs 1 个新 RPC，权衡后选 server 分支 |
| 新增 MoveEntity RPC | service 清晰（player_move vs npc_move）| 多 1 RPC；proto 序号 +1；a2a-gateway 兼容性测试要做 | 1.0 server 端区分简单；扩 1 个 RPC 是 2.0 量级 |
| Move() 只玩家，新加 NpcMove() | service 最清晰 | proto +1 RPC；server +1 handler；client +1 path | 同上 |
| 完全分开 service | - | 15 RPC 起步；service 定义重构 | 完全过度设计 |

### 实施影响

- `packages/proto/world.proto`：
  ```proto
  enum EntityType {
    ENTITY_TYPE_UNSPECIFIED = 0;
    ENTITY_TYPE_PLAYER = 1;
    ENTITY_TYPE_NPC = 2;
  }
  message MoveRequest {
    EntityType entity_type = 4;  // 新增；默认 PLAYER 向后兼容
    string entity_id = 5;         // 新增；player_id 字段弃用但保留
    // ...
  }
  ```
- `apps/world-engine/src/grpc.rs::move()`：加 `match entity_type` 分支
- `apps/api-gateway/internal/worldgrpc/client.go::Move`：发包填 entity_type=PLAYER + entity_id=player_id
- agent-os（T07 world_client）发包填 entity_type=NPC + entity_id=npc_id
- **不动**：现有 service trait / handler trait / 数据库 / metrics

## Q2：5 NPC 的固定 UUID 选什么

### 最终决策：**5 个 UUID 沿用现有 initdb seed 模式：`00000000-0000-0000-0000-00000000000{1..5}`**

### 理由

1. **与 demo 玩家 UUID 风格一致**：demo / admin 用 `11111111-...` `22222222-...` 前缀
2. **零前缀 + 顺序后缀**语义清晰："NPC 区"，编号 1-5
3. **initdb seed 稳定**：`docker compose down -v` 重建后 UUID 不变（NPC 不依赖外部 ID）
4. **未来加 NPC**：在 00000000-0000-0000-0000-000000000006+ 加即可

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：`00000000-...-{1..5}` | 与 demo/admin 一致；零前缀清晰 | 看起来像"假 UUID" | UUID v4 末位可任意；这只是约定 |
| UUID v7（时间序） | 真实 | 不固定 | 1.0 demo 重启 UUID 变 → script 失效（已知限制 #3）|
| UUID v4 随机 | 真实 | initdb 每次不同 | 同上 |
| 字符串 ID（"wang_boss_001"） | 可读 | 不兼容 UUID schema | PG schema 用 UUID |

### 实施影响

- `scripts/03-seed-npc-positions.sql`：
  ```sql
  INSERT INTO npc_position (npc_id, agent_id, x, y, tile_id, enabled)
  VALUES
    ('00000000-0000-0000-0000-000000000001', 'npc_wang_boss_001', 50, 50, 'tile_0_0', true),
    ('00000000-0000-0000-0000-000000000002', 'npc_lihua_001',   150, 50, 'tile_1_0', false),
    ('00000000-0000-0000-0000-000000000003', 'npc_xxx_003',     50, 150, 'tile_0_1', false),
    ('00000000-0000-0000-0000-000000000004', 'npc_xxx_004',    -50, -50, 'tile_-1_-1', false),
    ('00000000-0000-0000-0000-000000000005', 'npc_xxx_005',    150, 150, 'tile_1_1', false);
  ```
- `packages/npc-templates/*.yaml::agent_id` 字段对应上面 `agent_id`
- wang_boss.yaml 的 `npc_id` 字段填 `00000000-0000-0000-0000-000000000001`
- **不动**：player 表 demo/admin UUID（已固定）

## Q3：王老板初始 say 是 5 句还是循环 3 句

### 最终决策：**3 句循环随机**（Sprint 12 加 5 选项 talk_tree 是另一回事）

### 理由

1. **Sprint 11 范围最小**：3 句足够证明"NPC 会主动说话"
2. **每次进入 tile 不重复**：random_pick → 避免玩家每次听到同一句
3. **Sprint 12 升级**：5 选项 talk_tree 是"玩家回复"，不是"NPC 主动 say" —— 两件事不冲突
4. **yaml 简化**：3 句比 5 句好维护

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：3 句循环 | 简单；随机；不重复 | 内容少 | 1.0 demo 节奏快，3 句够 |
| 5 句轮换 | 更多样 | 重；写多 | 1.0 不演示重复进入 |
| 1 句固定 | 最简 | 每次听同一句，重复感 | 体验差 |
| 动态生成 | 灵活 | 1.0 无 LLM | 同 plan §六 拒绝 |

### 实施影响

- `packages/npc-templates/wang_boss.yaml::say.greeting[]` 3 句：
  ```yaml
  say:
    greeting:
      - "欢迎来到城邦！有什么可以帮你的吗？"
      - "新面孔啊，要不要来我店里坐坐？"
      - "城邦最近可热闹了，到处转转吧！"
  ```
- Sprint 12 T07 在此基础上加 `say.welcome[]`（welcome 专用）+ `talk_tree`（玩家回复分支）
- `apps/agent-os/src/agent_os/action_dispatcher.py::say()` 默认 random_pick
- **不动**：现有 yaml 字段结构

## Q4：agent-os port 用哪个

### 最终决策：**8084**（与现有 8080/8082/8083 平行）

### 理由

1. **端口分配规律**：
   - 8080 = api-gateway HTTP
   - 8082 = ws-gateway WS
   - 8083 = a2a-gateway HTTP
   - 8084 = agent-os HTTP（新增）
2. **8081 跳过**：历史上 docker 偶发占用
3. **不与 50051/50052 冲突**：gRPC port 不在 HTTP 范围
4. **a2a-gateway 50061 gRPC 不在 HTTP 范围**

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：8084 | 与现有 8080/8082/8083 平行 | 无 | - |
| 8080（复用 api-gateway）| 0 新端口 | agent-os 不该绑 api-gateway 同端口 | 一个容器一个端口 |
| 9000（避开常规）| 显眼 | 与其它 8000 段服务不一致 | 端口规整差 |
| 50051（world-engine）| - | 已被占用 | 同上 |
| unix socket | 0 端口 | 容器间 socket 共享复杂 | 1.0 简化 |

### 实施影响

- `apps/agent-os/src/agent_os/config.py::HTTP_PORT = 8084`
- `apps/agent-os/Dockerfile` EXPOSE 8084
- `docker-compose.yml` agent-os service：
  ```yaml
  agent-os:
    image: aitown/agent-os:latest
    ports:
      - "8084:8084"
    environment:
      - AGENT_OS_HTTP_ADDR=0.0.0.0:8084
      - AGENT_OS_WORLD_GRPC_ADDR=world-engine:50051
      - AGENT_OS_REDIS_URL=redis://redis:6379/0
    depends_on:
      world-engine: { condition: service_healthy }
      redis: { condition: service_healthy }
  ```
- **不动**：现有 7 容器的 port 分配

## Q5：玩家走近触发 say 的距离阈值

### 最终决策：**同 tile（玩家与 NPC 都在 `tile_X_Y`，即 `|Δx| < 100 ∧ |Δy| < 100`）**

### 理由

1. **与现有 3×3 tile 系统一致**：tile 是 100 世界单位的方格
2. **demo 演示友好**：玩家走 1 步（同 tile 内任意位置）即触发
3. **不引入"距离"概念**：1.0 无 NPC 视野 / 寻路，距离阈值简单即可
4. **listener 性能**：O(1) per tick（玩家数 × NPC 数；1 demo = 1 × 1 = 1）

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：同 tile | 简单；与 tile 系统一致 | 玩家在 tile 边缘可能"出 tile" | tile 中心判定，边缘情况忽略 |
| 50 世界单位（半 tile）| 更精确 | 需要算距离；listener 复杂 | 1.0 不需要 |
| 200 世界单位（2 tile）| 触发范围广 | 玩家走近 2 tile 就触发，过早 | demo 节奏不对 |
| 视野 cone（前向）| 真实感 | NPC 转向 + 视野计算 | 2.0+ |
| 始终触发（无论距离）| 最简 | 玩家远离也 say → 不真实 | 体验差 |

### 实施影响

- `apps/agent-os/src/agent_os/player_listener.py::is_in_range(player, npc)`：
  ```python
  def is_in_range(player_pos, npc_pos):
      return (
          abs(player_pos.x - npc_pos.x) < 100
          and abs(player_pos.y - npc_pos.y) < 100
      )
  ```
- 注意：tile 中心是 `(tile_x*100+50, tile_y*100+50)`；玩家 `tile_0_0 (50,50)` 与 NPC `tile_0_0 (50,50)` = 0 距离，触发
- `apps/agent-os/src/agent_os/loop.py`：tick 时 `for npc in registry: if is_in_range(p, n) and not welcomed: trigger_welcome()`
- **不动**：world-engine 坐标系（保持原状）

## Q7：agent-os health check 端点用哪个

### 最终决策：**`/healthz`（liveness）**（与现有 7 容器一致）

### 理由

1. **统一约定**：world-engine / api-gateway / ws-gateway / a2a-gateway 全部用 `/healthz`
2. **agent-os 简单**：进程在 = 健康；无需查 Redis/PG/wg 依赖
3. **不引入 `/readyz` 复杂度**：readyz 需要验证所有依赖，agent-os tick 是异步的，readyz 难定义

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：/healthz | 与 7 容器一致 | 不查依赖 | agent-os tick 异步；healthz 表达"进程在"足够 |
| /readyz（深检） | 严格 | 要查 Redis/PG/world-engine；agent-os tick 是 fire-and-forget | 1.0 简化 |
| 两者都加 | 完整 | agent-os 没必要 | 1.0 不演示"agent-os 准备好了" |
| /health | 短 | 与约定不一致 | 约定问题 |

### 实施影响

- `apps/agent-os/src/agent_os/main.py`：

## Q8：agent-os 用 FastAPI 还是裸 asyncio

### 最终决策：**FastAPI**（uvicorn + 1 个 FastAPI app，只为 `/healthz` 端点）

### 理由

1. **/healthz 已经要 HTTP server**：FastAPI 自然提供
2. **未来扩 endpoint 简单**：Sprint 12 agent-os 可能加 `/v1/agent/say` 等 endpoint（参 plan §六 拒绝清单，但未来可能开）
3. **依赖不重**：FastAPI + uvicorn 已是常见 Python web 栈；agent-os 其他逻辑（loop / BT / listener）独立于 web 框架
4. **测试简单**：httpx.AsyncClient mock /healthz 不依赖真实 server

### 已考虑方案对比

| 方案 | 优 | 劣 | 否决理由 |
|---|---|---|---|
| 当前 ✅：FastAPI | /healthz 自然；未来扩 endpoint | 多 1 依赖（fastapi + uvicorn） | 依赖已常见；扩 endpoint 时零成本 |
| 裸 asyncio（aiohttp 自写） | 0 额外依赖 | 要手写 router + middleware；不必要 | FastAPI 已解决 |
| starlette（FastAPI 底层）| 比 FastAPI 轻 | 路由 + OpenAPI 等要手写 | FastAPI 是 starlette + 实用工具 |
| Flask（同步）| 简单 | 同步阻塞；agent-os tick 异步 → 不一致 | 1.0 一致性 |
| gRPC only（无 HTTP）| 简洁 | docker healthcheck 用 HTTP，要绕开 | healthcheck 需 HTTP |

### 实施影响

- `apps/agent-os/pyproject.toml`：
  ```toml
  dependencies = [
    "fastapi>=0.110",
    "uvicorn[standard]>=0.27",
    "grpcio>=1.60",
    "grpcio-tools>=1.60",
    "redis>=5.0",
    "pyyaml>=6.0",
    "pydantic>=2.0",
  ]
  ```
- `apps/agent-os/src/agent_os/main.py`：FastAPI app + uvicorn 启动
- agent-os loop / BT / listener 是独立模块，不依赖 FastAPI（可独立测试）
- **不动**：其它 4 服务
