# Emotion Persistence Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:writing-plans to break this design into a task plan, then superpowers:subagent-driven-development to execute task-by-task.

**Goal:** Persist NPC emotion tags per turn and aggregate them into a continuous exponential-decay distribution for prompt injection, so NPC dialogue carries emotional inertia toward each player (fast decay) and the broader player base (slow decay).

**Architecture:** Runtime aggregation from existing `memory_player_session` table (add 1 column + 1 index). At prompt build time, run two SQL queries (per-player×NPC + per-NPC-global), apply exponential decay weights in Python, inject weighted distribution into system prompt.

**Tech Stack:** Python (agent-os), PostgreSQL (existing migration `pg-schema-2.0.sql` extension), Redis (unchanged), Go (no changes).

---

## 1. Background & Motivation

Stage 2 (closed in T28) introduced 8-class emotion tags on streamed NPC dialogue beats. The tag is validated by `EmotionValidator` and pushed via Redis to ws-gateway for real-time UI display, but **no persistence layer exists** — when a session ends, the emotion history evaporates.

Three pain points this fixes:

1. **No continuity**: NPC replies across sessions have no memory of the player's prior emotional arc ("you cheered me up last time")
2. **No global mood**: The same NPC cannot reflect a citywide trend (e.g., "everyone's been complaining lately")
3. **Lost analytics signal**: Stage 2 emotion data is one-shot — there's no way to investigate patterns post-hoc

User-confirmed scope (brainstorming session, 2026-10-06):
- **Use case**: NPC accumulated mood affects future dialogue tone (option 2)
- **Granularity**: both per-player×NPC AND per-NPC global coexist (option 3)
- **Decay model**: exponential decay with configurable τ (option 2)

## 2. Architecture

### Approach: Runtime aggregation from `memory_player_session`

**Why this over alternatives:**

| Option | Verdict |
|--------|---------|
| **A. Runtime aggregation** (chosen) | Always reflects true current state; exp decay weights computed at prompt time = mathematically pure; zero new infra |
| B. Materialized `npc_emotion_state` table | Faster read (1 row) but exp decay is inherently continuous — materialization always returns stale weights; extra updater infra |
| C. Redis ZSET counter | Very fast; adds cross-pod sync complexity; exp decay requires app-layer computation anyway |

User's choice of exponential decay (continuous, hard to predict) is the deciding factor: a materialized view would return weights that are *always* slightly wrong relative to true exp decay. Runtime aggregation is the natural fit.

### Flow

```
LLM stream produces "happy" beat
        ↓
dispatcher.say_stream() validates emotion
        ↓
ON npc_say_stream_done (Stage 2 existing hook):
        ↓
INSERT INTO memory_player_session (npc_id, player_id, message, emotion, created_at)
        ↓
...session ends / next prompt...

dispatcher.say_stream() called for new turn
        ↓
emotion_aggregator.fetch_distribution(npc_id, player_id):
    rows = SELECT emotion, created_at FROM memory_player_session
           WHERE npc_id=? AND player_id=? ORDER BY created_at DESC LIMIT 50
    return exp_decay_distribution(rows, now, τ_player)

emotion_aggregator.fetch_global_distribution(npc_id):
    rows = SELECT emotion, created_at FROM memory_player_session
           WHERE npc_id=? ORDER BY created_at DESC LIMIT 100
    return exp_decay_distribution(rows, now, τ_global)

prompt_template.render(npc_id, ..., recent=recent_dist, global=global_dist)
        ↓
LLM sees: "你最近 10 轮 70% happy；全局玩家 45% sad" → continues tone
```

## 3. Data Model

### Migration: `pg-schema-2.0-emotion.sql` (new file)

```sql
-- Emotion tag denormalized for fast aggregation query
ALTER TABLE memory_player_session ADD COLUMN emotion TEXT;

-- Index for the aggregation hot path: filter by npc+player, recent first, emotion grouping
CREATE INDEX IF NOT EXISTS idx_memory_player_session_emotion_recent
  ON memory_player_session(npc_id, player_id, created_at DESC, emotion);
```

**Why denormalize**: The aggregation query is `SELECT emotion, created_at FROM memory_player_session WHERE npc_id=? AND player_id=? ORDER BY created_at DESC LIMIT 50`. With the JSONB `message` blob, we'd need `->>'emotion'` extraction + functional index — slower + more storage. A nullable `emotion TEXT` column is one extra 8-byte pointer per row; trivial.

**Backfill**: Old rows pre-migration have `emotion = NULL`. Aggregation skips them (`emotion IS NOT NULL` filter).

### No new tables

`memory_player_session` already exists (`pg-schema-2.0.sql:23`). No new schema objects beyond the column + index.

### Env-driven tunables

| Env var | Default | Purpose |
|---------|---------|---------|
| `EMOTION_TAU_PLAYER_SECONDS` | `7200` (2h) | Per-player decay constant τ |
| `EMOTION_TAU_GLOBAL_SECONDS` | `86400` (24h) | Per-NPC-global decay constant τ |
| `EMOTION_PLAYER_LIMIT` | `50` | Max rows scanned for per-player query |
| `EMOTION_GLOBAL_LIMIT` | `100` | Max rows scanned for global query |
| `EMOTION_INJECT_ENABLED` | `true` | Kill switch (false = skip aggregation + injection) |

## 4. Aggregation Algorithm

### Module: `apps/agent-os/src/agent_os/emotion/aggregate.py`

```python
"""Emotion history aggregation with exponential time decay."""
from __future__ import annotations
import math
import time
from collections import defaultdict
from dataclasses import dataclass
from datetime import datetime, timezone
from typing import Iterable


@dataclass(frozen=True)
class EmotionRow:
    emotion: str
    created_at: datetime  # tz-aware


@dataclass(frozen=True)
class EmotionDistribution:
    weights: dict[str, float]   # emotion → normalized weight (sums to 1.0)
    raw_counts: dict[str, int]  # emotion → raw row count (pre-decay, for debugging)
    total_rows: int


def exp_decay_weight(age_seconds: float, tau_seconds: float) -> float:
    """Exponential decay: weight = exp(-Δt / τ). τ is the e-folding time.

    age = 0 → weight = 1.0
    age = τ → weight = 0.368
    age = 3τ → weight = 0.050 (effectively zero)
    """
    if tau_seconds <= 0:
        raise ValueError("tau_seconds must be > 0")
    return math.exp(-age_seconds / tau_seconds)


def aggregate_distribution(
    rows: Iterable[EmotionRow],
    *,
    now: datetime | None = None,
    tau_seconds: float,
) -> EmotionDistribution:
    """Compute exp-decay-weighted emotion distribution from history rows.

    Returns a normalized distribution where weights sum to 1.0 (or all zeros
    if `rows` is empty).
    """
    if now is None:
        now = datetime.now(timezone.utc)
    if tau_seconds <= 0:
        raise ValueError("tau_seconds must be > 0")

    weights: dict[str, float] = defaultdict(float)
    raw_counts: dict[str, int] = defaultdict(int)
    total = 0.0
    n = 0
    for row in rows:
        if not row.emotion:  # skip NULL (pre-migration backfill)
            continue
        age = max(0.0, (now - row.created_at).total_seconds())
        w = exp_decay_weight(age, tau_seconds)
        weights[row.emotion] += w
        raw_counts[row.emotion] += 1
        total += w
        n += 1

    if total > 0:
        weights = {e: round(w / total, 3) for e, w in weights.items()}
    else:
        weights = {}

    return EmotionDistribution(
        weights=dict(weights),
        raw_counts=dict(raw_counts),
        total_rows=n,
    )


def format_distribution_for_prompt(dist: EmotionDistribution) -> str:
    """Render distribution as compact text for prompt injection.

    Always shows all 8 emotion classes (zero-weighted → '0.000') so the LLM
    sees the complete label set.
    """
    from agent_os.stream.emotion_validator import ALLOWED_EMOTIONS
    parts = []
    for emo in sorted(ALLOWED_EMOTIONS):
        w = dist.weights.get(emo, 0.0)
        parts.append(f"{emo}={w:.3f}")
    return ", ".join(parts)
```

### Module: `apps/agent-os/src/agent_os/emotion/repository.py`

Wraps SQL queries. Uses existing `asyncpg` pool (already wired in agent-os for `memory_player_session`).

```python
"""PG repository for emotion history aggregation."""
from __future__ import annotations
import os
from datetime import datetime, timezone

import asyncpg

from .aggregate import EmotionDistribution, EmotionRow, aggregate_distribution


class EmotionRepository:
    def __init__(self, pool: asyncpg.Pool):
        self._pool = pool
        self._tau_player = float(os.getenv("EMOTION_TAU_PLAYER_SECONDS", "7200"))
        self._tau_global = float(os.getenv("EMOTION_TAU_GLOBAL_SECONDS", "86400"))
        self._player_limit = int(os.getenv("EMOTION_PLAYER_LIMIT", "50"))
        self._global_limit = int(os.getenv("EMOTION_GLOBAL_LIMIT", "100"))

    async def fetch_player_distribution(
        self, npc_id: str, player_id: str,
    ) -> EmotionDistribution:
        async with self._pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT emotion, created_at FROM memory_player_session
                WHERE npc_id = $1 AND player_id = $2
                  AND emotion IS NOT NULL
                ORDER BY created_at DESC
                LIMIT $3
                """,
                npc_id, player_id, self._player_limit,
            )
        return aggregate_distribution(
            (EmotionRow(emotion=r["emotion"], created_at=r["created_at"]) for r in rows),
            tau_seconds=self._tau_player,
        )

    async def fetch_global_distribution(
        self, npc_id: str,
    ) -> EmotionDistribution:
        async with self._pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT emotion, created_at FROM memory_player_session
                WHERE npc_id = $1
                  AND emotion IS NOT NULL
                ORDER BY created_at DESC
                LIMIT $2
                """,
                npc_id, self._global_limit,
            )
        return aggregate_distribution(
            (EmotionRow(emotion=r["emotion"], created_at=r["created_at"]) for r in rows),
            tau_seconds=self._tau_global,
        )
```

### Top emotion helper

```python
def top_emotion(dist: EmotionDistribution) -> str:
    if not dist.weights:
        return "无"
    return max(dist.weights, key=dist.weights.get)
```

### `MemoryWriter.write_emotions` (extend existing)

```python
async def write_emotions(
    self, *, npc_id: str, player_id: str, session_id: str, emotions: list[str],
) -> None:
    """Insert one row per emotion into memory_player_session.

    Each emotion corresponds to one beat in the stream. Empty list → no-op.
    """
    if not emotions:
        return
    async with self._pool.acquire() as conn:
        # Stage 2 already writes `message` JSONB; we just add the denorm `emotion` col
        await conn.executemany(
            """
            INSERT INTO memory_player_session (npc_id, player_id, message, emotion)
            VALUES ($1, $2, $3::jsonb, $4)
            """,
            [(npc_id, player_id, json.dumps({"session_id": session_id, "type": "emotion"}), e)
             for e in emotions if e],
        )
```

**Note**: This piggybacks on existing `memory_player_session` inserts. Stage 2's memory writer already inserts per-turn records (for short-term history). We extend those rows to include the emotion column. If Stage 2 already inserts a row, we update it; otherwise we insert a new minimal row.

## 7. Failure Modes

| Scenario | Behavior |
|----------|----------|
| PG unavailable (pool acquire fails) | Skip aggregation; inject "（情绪历史暂不可用）"; log warning |
| Empty history (first interaction) | Inject "（首次对话，无历史情绪）"; no inertia hint |
| `emotion IS NULL` (pre-migration backfill) | Skip that row; aggregation excludes it |
| > LIMIT rows | Take most recent N; exp decay makes older negligible anyway |
| τ = 0 (misconfig) | `ValueError` raised in `aggregate_distribution`; caught + logged warning |
| Emotion with weight 0.000 | Still rendered in prompt (LLM sees full label set) |
| Write path fails | Logged warning; stream continues (best-effort persistence) |

### No new error codes

Aggregation failures are logged as warnings; they do NOT raise user-visible errors. The stream itself is unaffected (writes are best-effort, reads fall back to no-injection). If a future REST endpoint exposes aggregation status, a new code can be added then — YAGNI for now.
